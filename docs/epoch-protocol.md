# Epoch randomness protocol

D20 provides general randomness requests using API3-signed input data, a fixed operational VRF key and public evidence. Epochs last 200 blocks. The keeper prepares snapshots locally; idle epochs produce no keeper publication transaction.

## Request and publication

The registry's first epoch starts 200 blocks after proxy initialization. For epoch e, start=firstEpochStart+(e-1)*200. Each epoch uses the catalog in force for it: an ordered list of count sources (1 to 10), each a recipe and its signer. Source selection hashes the catalog hash, epoch ID and canonical block hash at start-1, then takes modulo count. If the selected source yields no valid packet, fallback attempt n (1 to count−1) uses source (selected+n) mod count with that slot's recipe and signer. getEpochFallbackSelection(epochId, n) returns it (source slot, recipe id, signer, selector, queryHash and canonical request), sourceCountAt(epochId) gives count, fallbackOpensAt(epochId, n) is start+n×20 (FALLBACK_DELAY_BLOCKS), and commitEpochFallback(epochId, n, attestation) accepts it only from that block; commitEpoch is attempt 0 and is valid from the epoch start. An attempt at or beyond count reverts with InvalidFallback, and with at most ten sources the last window opens 180 blocks into the 200-block epoch. The epoch record stores the committed source slot, so the attempt is (source−selected) mod count. Requests checkpoint that canonical source anchor while it is within BLOCKHASH's 256-block window.

A request fixes its consumer, client seed, mapping, refund address, request block, epoch ID and 60-second deadline. It escrows the fee quoted in its own transaction, max(minFee, feeMultiplier × block.basefee × (fulfillGasOverhead + callbackGasLimit)), even if that epoch's API record is not published yet; anything sent above the quote becomes refund credit of the refund address. Contracts quote with quoteFee in the requesting transaction; off-chain senders quote with quoteFeeAt and the header base fee plus a buffer, because eth_call commonly reports a zero base fee. Before initial activation, requests revert. The keeper publishes its first validated saved snapshot only when a live paid request needs it. It never refreshes a persisted snapshot to obtain another result, and moves to another source only through the fallback ladder, after the current source produced no valid packet and once the next window is open.

Once published, the epoch record cannot be overwritten by this implementation. The randomness target is max(requestBlock, committedBlock+1). That block is strictly after publication, so the final block-hash input is unknown when the API packet is committed. A missing publication has no usable target or VRF seed. Multiple pending requests share the published packet; each has its own fixed request context and proof. An older epoch may be published/served across a boundary while its requests remain timely.

## Recipes and catalogs

Recipes live in an owner-managed, append-only registry in EpochEntropy. A recipe is three values: the canonical request, whose keccak256 is the query hash the Airnode signs; a data template describing the exact signed record it accepts; and the JSON body a keeper posts to the provider's gateway. registerRecipe(canonicalRequest, template, body) is owner-only and appends the next id (0 to 255, MAX_RECIPES = 256), emitting RecipeRegistered(recipe, queryHash, canonicalRequest, template, body). A registered recipe can never be edited or removed, so a changed listing becomes a new id; catalogs choose among registered ids. Registration requires a canonical request of 1 to 1024 bytes, a body of 1 to 2048 bytes and a well-formed template, which keeps every EpochCommitted packet within its 2048-byte bound. The contract does not parse the body: keepers refuse to fetch unless the body canonicalizes to the canonical request. recipeCount(), getRecipe(id) (query hash, canonical request, template, body) and recipeRequest(id) read the registry; an unknown id reverts with InvalidConfig.

A registry registers six built-in recipes itself, at initialization or, for a registry initialized before the recipe registry, in its upgrade (initializeRecipeRegistry, run as the upgradeToAndCall data):

| Recipe | Provider | Query | Exact signed record |
| --- | --- | --- | --- |
| 0 | Hyperliquid | metaAndAssetCtxs, dex "", projection symbol `/0/universe/0/name` and value `/1/0/dayNtlVlm` | `{"symbol":"BTC","value":"<decimal>"}` |
| 1 | dRPC | jsonRpc on Ethereum mainnet: eth_call of Multicall3 `0xcA11bde05977b3631167028862bE2a173976CA11` getLastBlockHash() (`0x27e86d6e`) at `latest` | `{"id":null,"jsonrpc":"2.0","result":"0x<64 lowercase hex>"}` (105 bytes) |
| 2 | TickerLayer | lastTrade, assetClass crypto, BTCUSD | `{"symbol":"BTCUSD","price":<number>,"size":<number>,"timestamp":<integer, 1 to 16 digits>}` |
| 3 | TickerLayer | lastTrade, assetClass crypto, ETHUSD | as recipe 2 with ETHUSD |
| 4 | Nodary | latestFeeds, name ETH/USD (first-party, no projection) | `{"ETH/USD":{"value":<number>,"timestamp":<13-digit milliseconds>,"category":"crypto"}}` |
| 5 | dRPC | as recipe 1 on network base | as recipe 1 |

Ids 0 to 3 keep the canonical requests of the catalog implementation that precedes the registry, so the initial catalog and every epoch committed under it select, commit and replay unchanged. The first mainnet implementation used ANU random numbers at id 1 instead of the Ethereum block hash; no epoch was ever committed from that slot on either public registry (checked on 2026-09-17: two published mainnet epochs, both recipe 2, and sixty testnet epochs from recipes 0, 2 and 3), so no published epoch needs the ANU definition to replay. Until the rollout catalog takes effect on mainnet, slot 1 of its initial catalog pairs recipe 1 with the retired provider's Airnode, which signs no Ethereum block hash, so that slot yields no packet and falls back after 20 blocks, as it does today. Evidence recorded before the registry that did use ANU replays when its definition is supplied as a recipe book entry. The Hyperliquid SOL mid and Nodary BTC/USD listings of the previous implementation are not built in; config/recipes holds recipe files for registering them. The previous ids 4 to 7 were never used by a scheduled catalog on either public registry, and the upgrade step refuses a registry that has one.

### Data templates

A template is a byte sequence of segments, each an opcode and its operands:

| Opcode | Segment | Operands | Matches |
| --- | --- | --- | --- |
| `0x01` | LITERAL | length n (1 to 128), then n bytes | exactly those bytes |
| `0x02` | HEX | n (1 to 128) | exactly n characters `0-9a-f` |
| `0x03` | DECIMAL | flags (0 to 3) | an unsigned JSON number: `0` or a nonzero digit followed by digits, then an optional fraction `.digits` when flags & 1 and an optional exponent `(e\|E)(+\|-)?digits` when flags & 2 |
| `0x04` | INTEGER | min, max (1 ≤ min ≤ max ≤ 128) | a nonzero digit followed by digits, with min to max digits |

Variable segments are greedy and never backtrack; a record is accepted only when the segments consume it exactly, so there are no trailing bytes, and it is at most 128 bytes. A well-formed template is at most 256 bytes, contains at least one variable segment and has a shortest possible match of at most 128 bytes. The segments are the smallest set that expresses every record the providers sign: literals fix key order, names and punctuation; HEX covers hashes and fixed-length random values; DECIMAL covers JSON numbers and decimal strings with the two grammar options the providers need; INTEGER covers bounded positive integers such as millisecond timestamps, which DECIMAL cannot bound. For example recipe 1's template is LITERAL(39) `{"id":null,"jsonrpc":"2.0","result":"0x`, HEX(64), LITERAL(2) `"}`, and recipe 2's is LITERAL `{"symbol":"BTCUSD","price":`, DECIMAL(3), LITERAL `,"size":`, DECIMAL(3), LITERAL `,"timestamp":`, INTEGER(1, 16), LITERAL `}`. An ANU-style array of four hex8 values is LITERAL `{"success":true,"type":"hex8","length":"4","data":["`, then HEX(16) and LITERAL `","` alternating, and LITERAL `"]}`.

The contract (contracts/libraries/DataTemplate.sol), the replay library (src/templates.ts: encodeDataTemplate, decodeDataTemplate, matchesDataTemplate) and the keeper (keeper/src/template.rs) share the verdicts in test/fixtures/epoch-data-cases.json. The built-in templates accept exactly the bytes the previous per-recipe validators accepted: test/DataTemplate.test.ts compares them against copies of those validators on every single-byte mutation of the real signed samples. A decimal is `0` or a digit sequence without a leading zero, with an optional fraction; a number is the unsigned JSON form of the same, with an optional exponent, exactly as JSON.stringify writes it (Nodary values such as `76634.54000000001` keep their binary64 digits). Records are the exact bytes above in that key order: no whitespace, extra fields, reordered keys, escaped characters, other names or symbols, uppercase hex or other lengths.

### Canonical requests and catalogs

A canonical request is AirnodeHub's canonical form, the JSON of [operation, canonical(parameters)] with canonical(responseProjection) appended when present, where every object at any depth becomes its [key, value] entries sorted by key and arrays keep their order; queryHash is keccak256 of its UTF-8 bytes. For example recipe 1 is `["jsonRpc",[["method","eth_call"],["network","ethereum"],["params",[[["data","0x27e86d6e"],["to","0xcA11bde05977b3631167028862bE2a173976CA11"]],"latest"]]]]` (queryHash `0xabe6d1ad9b60d0fb0a11fdb29f33b005bf366921961e833a62ba7f9c0098abda`). The keeper reads a selected recipe from the registry (cached by id), refuses to fetch unless the selection carries that recipe's canonical request and hash, the body canonicalizes to it and the template is well-formed, posts the registered body byte for byte to the gateway of the slot's signer, and validates the signed record with the template before saving it. A refused source is recorded as failed, so the fallback ladder continues. SECURITY.md describes what each attestation does and does not establish.

A registry starts with its initial catalog: recipes 0, 1, 2 and 3 with the four signers given at initialization, hashed as keccak256(abi.encode(RECIPE_DOMAIN, address[4] signers)) and bound into protocolConfigurationHash; catalogHash() and the getters hyperliquidSigner, ethereumBlockSigner, btcTradeSigner and ethTradeSigner keep it. The owner replaces it for future epochs with scheduleCatalog(recipes, signers, fromEpoch): 1 to 10 distinct registered recipe ids with nonzero signers in slot order, for an epoch at least two ahead of the current one; a still-pending version is replaced and an active one never is. Its hash is keccak256(abi.encode(RECIPE_DOMAIN, uint8[] recipes, address[] signers)), and it emits CatalogScheduled(fromEpoch, catalogHash, recipes, signers). catalogAt(epochId) returns the hash, recipes and signers an epoch selects and commits with, and Epoch.catalogHash records that hash, so the current and next epoch, prepared snapshots and open requests never change catalog. The rollout catalog is [0, 1, 2, 4, 5] with each provider's Airnode (Hyperliquid, dRPC, TickerLayer, Nodary, dRPC): neighbouring slots, including the last and the first, never share a signer, so every fallback moves to another provider.

Raw signed data is at most 128 bytes; it is never cropped. Low-s 65-byte EIP-191 signatures bind the canonical query, signed timestamp and exact data. At publication the signed timestamp cannot be in the future or older than 240 seconds (MAX_ATTESTATION_AGE; the keeper stops sending a snapshot at the same age). Object envelopes are reconstructed with round-trip binary64 parsing and ECMAScript number formatting; raw string envelopes remain unchanged.

Equal provider data across epochs is allowed. Epoch parameters produce distinct commitments; hashing repeated data is not a claim of fresh independent entropy. If the first saved response becomes stale, it cannot be refreshed to rescue a request. The unfulfilled request retains its refund path.

## Proof and settlement

The VRF seed binds chain ID, coordinator proxy, key hash, request ID, consumer, client seed, mapping hash, request block, resolved target block/hash, epoch ID and epoch hash. Fulfillment submits only request ID plus real VRF proof: 452 calldata bytes. The non-indexed FulfillmentEvidence packet is 416 bytes. fulfillRandomnessBatch accepts up to 16 request/proof pairs and runs each exactly like fulfillRandomness (same events, evidence, settlement and callback); members already fulfilled, refunded or expired are skipped with FulfillmentSkipped(requestId, reason: 1 fulfilled, 2 refunded, 3 expired), and any proof or readiness failure reverts the whole batch. EpochCommitted separately archives the full canonical query and signed API packet once.

Valid proof acceptance at or before the request deadline earns the fee, including when its callback fails. Each request stores the fee it escrowed (requestFeePaid); keeper share, treasury share and refund all settle from that stored amount, never from the live fee, so a later fee change cannot alter what an open request pays or refunds. A configured basis-point share is paid to the wallet that submitted the accepted proof when the registry authorizes it to publish epochs (isAuthorizedCommitter: the current committer or an allowed backup committer), and to committer() for any other submitter, so an arbitrary submitter is never paid. A registry that does not answer that view, or whose call reverts, also pays committer(). Failed keeper transfers become backed keeper credits. The remainder becomes treasury earnedFees. Neither path spends pending-request escrow or refund credits. Callback retries keep the same result and never pay another keeper share. Expired unfulfilled requests remain refundable to their original recipient by transaction: the refund is feePaid × refundBps / 10000 using the ratio snapshotted into the request at creation (requestRefundBps; owner-set between 5,000 and 10,000 bps for future requests, default 10,000) and the remainder becomes earnedFees.

## Administration and verification

EpochEntropy and D20VRFCoordinator run behind atomically initialized ERC1967 proxies with owner-authorized UUPS upgrades. Ownership transfers require acceptance by the proposed owner. The registry owner can rotate the committer and allow up to four backup committers (setBackupCommitter, BackupCommitterSet, isBackupCommitter), which may publish epochs under exactly the committer's rules and are paid the keeper share of the requests whose accepted proofs they submit themselves (isAuthorizedCommitter), while any other submitter's fulfillment pays committer(); coordinator owner can change fee recipient, keeper share, pricing (setPricing, bounded to minFee at most 10 native units, multiplier 0–20 and overhead 100,000–2,000,000 gas) and the expiry refund ratio (setRefundBps, never below 50%). The registry owner can also register recipes, which are append-only and never edited, and schedule catalogs, which apply only to future epochs and are never rewritten for a current or published one. This implementation has no VRF-key or request-input setter. Upgrade authority can change code, so it is a trust assumption, not an immutable guarantee against governance.

Replay uses the initialized configuration, including initialFeeRecipient and initialMinFee rather than the mutable payout address and live pricing. Verify trusted chain/receipt data, source anchor, the fallback attempt implied by the committed source and its window (publication block at least start+attempt×20), request block, actual publication block/time, target=max(requestBlock,commitBlock+1), signatures and recipes (with the catalog in force for that epoch, from catalogAt, or CatalogScheduled events and the initial catalog, and each selected recipe's definition, from getRecipe or RecipeRegistered events), VRF and transcript. The replay library's resolveEpochCatalog turns a catalogAt view into the catalog replay expects and recognizes the initial catalog by its hash; its recipeBook defaults to the built-in recipes, and readEpochRecipes reads any other registered recipe, checked against its query hash. Resolve the implementation history of both proxies for the relevant transactions; proxy addresses/code alone do not identify execution logic. The current protocol has one packet schema; no alternate decoder modes are included.

The keeper pins both proxy implementation addresses/runtime hashes in addition to proxy/configuration identity and fails closed on unreviewed changes. Upgrade operations require storage-layout review and request/epoch/fee/replay regression tests. Current local layout baselines are in storage-layout/.

### Changing recipes and catalogs

Adding a listing is a registration, not an upgrade: the owner registers the recipe (admin.ts register-recipe checks a recipe file's body, template, signer and a signed sample first) and then schedules a catalog that lists its id with its Airnode. Recipes are never edited or removed, so a changed gateway listing becomes a new id and older epochs keep replaying with the recipe they used. Keepers need no update for a new recipe: they read it from the registry. They do need a gateway for each Airnode they serve, built in for the four providers above or set in EPOCH_API_ENDPOINTS.

The upgrade that introduced the registry replaces the hardcoded recipes of 640b60c (Arc Mainnet) and 96cc722 (Arc Testnet). Its storage keeps every declared slot of both layouts: slot 8 (640b60c's empty four-signer catalog array, 96cc722's retired uint256, zero on both registries) stays reserved, slot 9 holds the catalog array (unused gap on 640b60c, empty on 96cc722), and the gap gives up three slots: the recipe array takes slot 10, the backup committer mapping slot 11 and its count slot 12, so the gap shrinks from 38 to 35 and the layout still ends at slot 47. The upgrade call data runs initializeRecipeRegistry, which registers the built-in recipes once (reinitializer 2, owner-only) and refuses a registry with a non-empty slot 8 or a scheduled catalog, whose recipe ids would change meaning. Until the owner schedules the rollout catalog, epochs keep the initial catalog: its slot 1 pairs recipe 1 with the initial signer, which on both public registries is the retired provider's Airnode, so a slot 1 selection yields no valid packet and falls back to the next slot after 20 blocks, as it already does. The initial catalog, catalogHash() and protocolConfigurationHash do not change. No epoch on either public registry was committed from slot 1, so the current replay library verifies all of their published epochs; other deployments must replay each epoch with the recipes of the implementation active when it was committed. The rollout steps are in [the registry upgrade runbook](registry-upgrade.md).
