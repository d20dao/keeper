# Epoch randomness protocol

D20 provides general randomness requests using a public randomness beacon, a fixed operational VRF key and public evidence. Epochs last 200 blocks. An epoch's source is a recipe of its catalog: a round of the drand evmnet beacon, or a signed API record, the mechanism that served the epochs before the drand catalog and stays in the contract. Both networks now run the drand catalog, recipe 11 alone: Arc Testnet from epoch 11319 and Arc Mainnet from epoch 12448. The keeper prepares drand rounds locally; idle epochs produce no keeper publication transaction.

History (2026-10-02): the epochs before Arc Testnet epoch 11319 and Arc Mainnet epoch 12448 were published from signed API records (recipes 0 to 10), and replay still verifies them with the recipes and catalogs in force for them.

## Request and publication

The registry's first epoch starts 200 blocks after proxy initialization. For epoch e, start=firstEpochStart+(e-1)*200. Each epoch uses the catalog in force for it: an ordered list of count sources (1 to 10), each a recipe and its signer. Source selection hashes the catalog hash, epoch ID and canonical block hash at start-1, then takes modulo count. If the selected source yields no valid packet, fallback attempt n (1 to count−1) uses source (selected+n) mod count with that slot's recipe and signer. getEpochFallbackSelection(epochId, n) returns it (source slot, recipe id, signer, selector, queryHash and canonical request), sourceCountAt(epochId) gives count, fallbackOpensAt(epochId, n) is start+n×20 (FALLBACK_DELAY_BLOCKS), and commitEpochFallback(epochId, n, attestation) accepts it only from that block; commitEpoch is attempt 0 and is valid from the epoch start. An attempt at or beyond count reverts with InvalidFallback, and with at most ten sources the last window opens 180 blocks into the 200-block epoch. A catalog of one source, such as the drand catalog, has no fallback attempt: commitEpoch is its only way to publish. The epoch record stores the committed source slot, so the attempt is (source−selected) mod count. Requests checkpoint that canonical source anchor while it is within BLOCKHASH's 256-block window.

A request fixes its consumer, client seed, mapping, refund address, request block, epoch ID and 60-second deadline. It escrows the fee quoted in its own transaction, max(minFee, feeMultiplier × block.basefee × (fulfillGasOverhead + callbackGasLimit)), even if that epoch's packet is not published yet; anything sent above the quote becomes refund credit of the refund address. Contracts quote with quoteFee in the requesting transaction; off-chain senders quote with quoteFeeAt and the header base fee plus a buffer, because eth_call commonly reports a zero base fee. Before initial activation, requests revert. The keeper publishes its first validated saved snapshot only when a live paid request needs it. It never refreshes a saved signed record to obtain another result, and moves to another source only through the fallback ladder, after the current source produced no valid packet and once the next window is open. A saved beacon round that grows too old before its epoch is published is the one exception (see the refresh rule below).

Once published, the epoch record cannot be overwritten by this implementation. The randomness target is max(requestBlock, committedBlock+1). That block is strictly after publication, so the final block-hash input is unknown when the packet is committed. A missing publication has no usable target or VRF seed. Multiple pending requests share the published packet; each has its own fixed request context and proof. An older epoch may be published/served across a boundary while its requests remain timely.

## Recipes and catalogs

Recipes live in an owner-managed, append-only registry in EpochEntropy. A recipe is three values: the canonical request, whose keccak256 is the query hash its records are bound to (for a signed recipe, the query the Airnode signs); a data template describing the exact record it accepts; and the body naming what a keeper fetches, for a signed recipe the gateway request that keepers up to 0.4.0 sent, a JSON object posted to the gateway or a passthrough request (below), and for a beacon the same string as the canonical request. A recipe is one of two kinds. A beacon recipe has a registration and its record is a round of a public randomness beacon (next section); a signed API recipe has none and its record is signed by an Airnode. registerRecipe(canonicalRequest, template, body) is owner-only, registers a signed API recipe and appends the next id (0 to 255, MAX_RECIPES = 256), emitting RecipeRegistered(recipe, queryHash, canonicalRequest, template, body); registerBeacon appends a beacon the same way. A registered recipe can never be edited or removed, so a changed listing becomes a new id; catalogs choose among registered ids. Registration requires a canonical request of 1 to 1024 bytes, a body of 1 to 2048 bytes and a well-formed template, which keeps every EpochCommitted packet within its 2048-byte bound. The contract does not parse the body. Keepers prepare epochs from beacon recipes only (0.4.1 and later), and refuse a beacon unless its registration, request, body and template agree; they refuse every other recipe. recipeCount(), getRecipe(id) (query hash, canonical request, template, body) and recipeRequest(id) read the registry; an unknown id reverts with InvalidConfig.

### Beacon recipes

A beacon recipe names a public randomness network instead of a gateway request. registerBeacon(verifier, chainHash, publicKey, genesis, period, sampleRound, sampleSignature) is owner-only. It appends the next recipe id and emits RecipeRegistered and BeaconRegistered(recipe, verifier, chainHash, publicKey, genesis, period).

The recipe's canonical request and body are one string, `["drand","0x<chain hash>"]`, with the hash in lowercase hex (78 characters). Its template is one INTEGER(1, 19) segment, `0x040113`: a round number in decimal. The registration is stored beside the recipe and never changes. beaconOf(recipe) returns it as (verifier, genesis, period, chainHash, publicKey); a zero verifier marks a signed recipe, and an unknown id reverts with InvalidConfig. Round r is scheduled at genesis + (r − 1) × period.

registerBeacon reverts with InvalidConfig unless the verifier has code; the chain hash, genesis, period and sample round are nonzero; the sample round is not scheduled after the block's time; the verifier accepts the 128-byte key (isValidPublicKey); and it accepts the sample round's signature under the key (verifyRound). Both questions are asked as a commit asks its own, under the gas allowance and with the bounded answer below. A malformed key, and a verifier that reverts, runs out of gas or answers badly, cannot register. If the sender's gas cannot give the verifier its whole allowance, the call reverts with BeaconGasTooLow and not with InvalidConfig. The registry does not check that the chain hash names the network of the key, or that the verifier's code is the reviewed one: the owner vouches for the registration, which BeaconRegistered publishes.

slotSigner(recipe) is the signer a catalog lists for a beacon: address(uint160(keccak256(abi.encode(BEACON_DOMAIN, verifier, chainHash, keccak256(publicKey), genesis, period)))), with BEACON_DOMAIN = keccak256("D20_EPOCH_BEACON"). It is an identity derived from the registration, not a key, and zero for a signed recipe. scheduleCatalog reverts with InvalidConfig for any other signer in a beacon's slot, so a catalog hash binds the whole registration. verifyBeacon(recipe, round, signature) returns whether the recipe's verifier accepts the signature, and false for a signed recipe.

An epoch served by a beacon commits one round. The data is the round number in decimal, without a leading zero, at most 19 digits. The timestamp is genesis + (round − 1) × period exactly. The signature is the round's 64-byte BLS signature, a G1 point as x ‖ y in drand's serialization. commitEpoch and commitEpochFallback check, in this order:

1. The caller is the committer or a backup committer (OnlyCommitter).
2. The epoch is unpublished (AlreadyCommitted) and the attempt's window is open (FallbackNotOpen).
3. The timestamp is not in the future and at most 240 seconds old (InvalidTime; MAX_ATTESTATION_AGE).
4. The data matches the template (InvalidData).
5. The timestamp equals the round's scheduled time (InvalidTime).
6. The recipe's verifier accepts the signature under the registered key (InvalidSigner).

The verifier is called with BEACON_VERIFY_GAS, 400,000 gas, and the registry reads at most 32 bytes of its answer, so a verifier cannot make the registry pay to copy a large return. Only an exact 32-byte true counts. A revert, an exhausted allowance, no answer, another word or a longer answer is an invalid signature, so a hostile verifier costs a commit at most that allowance plus the registry's own work. registerBeacon asks isValidPublicKey the same way, and anything but an exact true is an invalid key.

The allowance is checked before it is given. A call forwards at most 63/64 of the gas left after its own cost (EIP-150), so under a low gas limit a valid verifier could be cut short, answer no, and a valid round would read as an invalid signature. Before each verifier call the registry therefore requires gasleft() to be at least BEACON_VERIFY_GAS + BEACON_VERIFY_GAS / 63 + 5,000, which is 411,349: the allowance, the 63/64 rule's share of it and a margin for the call's own cost. With less it reverts with BeaconGasTooLow. commitEpoch, commitEpochFallback, registerBeacon and the verifyBeacon view all do, so none of them answers false, InvalidSigner or InvalidConfig for want of gas. A beacon commit succeeds from a gas limit of about 511,000, and eth_estimateGas returns a limit of that size, so the keeper's estimate × 1.2 + 50,000 clears it; a fixed limit below it does not. verifyBeacon, called with eth_call, needs about 461,000.

No Airnode signs a beacon record and the digest of a signed record is not used: the beacon signs the round, and the timestamp is a function of it. Any round scheduled within the 240 seconds before the commit block is valid, including one from before the epoch's start. At a 3-second period that is up to 81 rounds, and which one an epoch commits is the committer's choice. One round can serve up to three consecutive epochs: an epoch lasts 200 blocks, about 100 seconds at Arc's block time, and a round stays valid for 240 seconds. The epoch hashes still differ, because each commitment binds its epoch ID, start block and anchor, but dataHash and attestationHash can repeat across those epochs, and so can the round's signature. An indexer must not key an epoch on any of them: the epoch ID, or its epoch hash, identifies one. Commitment, attestation hash and EpochCommitted are as for a signed record. The packet, abi.encode(canonicalRequest, (timestamp, data, signature)), is 448 bytes for every round. A beacon commit uses about 475,000 gas, about one verifier call more than a signed commit, and registerBeacon about 620,000.

D20BeaconVerifier is stateless, with no owner and no upgrade path. It is built on the unmodified kevincharm/bls-bn254 library (contracts/vendor/bls-bn254, pinned by npm run vendor:check) and checks the scheme of drand's evmnet, bls-bn254-unchained-on-g1. A round's signature is the BLS signature of the G1 point that RFC 9380 hash-to-curve gives for keccak256(r as 8 big-endian bytes), with expand_message_xmd over keccak256, the Shallue-van de Woestijne map and DST BLS_SIG_BN254G1_XMD:KECCAK-256_SVDW_RO_NUL_. verifyRound(publicKey, round, signature) checks e(signature, G2) = e(H(r), publicKey) with one two-pair call of the BN254 pairing precompile. Keys and signatures use drand's serialization of 32-byte big-endian words: x ‖ y for G1 and x_im ‖ x_re ‖ y_im ‖ y_re for G2, the word order of the pairing input.

Invalid input returns false, without reverting or burning the caller's gas: a signature that is not 64 bytes, a key that is not 128, a coordinate not below the field order, a point off the curve, the zero encoding of infinity. The verifier checks the points first. The pairing precompile uses all the gas it is given when a point is invalid, so it gets a fixed allowance of 200,000 gas (PAIRING_GAS; a two-pair check costs 113,000 under EIP-1108). If less than PAIRING_GAS + PAIRING_GAS / 63 + 1,000 gas is left when the pairing is due, verifyRound reverts with InsufficientGas instead of answering, because a valid signature would be cut short in the precompile and read as invalid; invalid input, which is refused before that point, still returns false and needs none of that gas. A direct call of a valid round needs a gas limit of about 285,000. G1 has cofactor 1, so the curve check is its group check. A G2 key outside the subgroup is refused by the precompile, so a verified signature establishes the key's membership; isValidPublicKey(publicKey) checks a key's encoding without that. A valid verification uses about 175,000 gas (a direct call as a transaction costs about 190,000 with its intrinsic gas and calldata), well inside BEACON_VERIFY_GAS. src/beacon.ts (verifyBeaconRound, beaconRoundMessage) computes the same hash and pairing check in TypeScript, and test/BeaconVerifier.test.ts holds the two to the same verdict on real evmnet rounds and on malformed input.

### Beacon epochs in the keeper

For a beacon recipe the keeper reads beaconOf for a recipe whose canonical request starts with `["drand","`, and fetches only a consistent registration: a verifier, a schedule with a period under 200 seconds, and the canonical request, body and template that registerBeacon writes. A beaconOf that reverts on the source's second attempt or later fails that source for good, so a catalog with another source falls back to it. A recipe that is no beacon at all, a signed API recipe, fails its source for good at once: the keeper logs an error ending with "signed API recipes are not supported since 0.4.1", reports the health fault `epoch_recipe_unsupported:<recipe>` until an epoch's selected source is supported again, and prepares the epochs after it as usual; requests of epochs the registry already published are served as always, and live paid demand on the epoch that cannot be prepared is the `epoch_stalled` fault with the reason `unsupported_recipe`.

Rounds come from the relays in DRAND_RELAYS, at most 8, four public drand relays by default (HTTPS, or loopback HTTP on chain 31337). Every relay whose circuit is closed is asked at once for `<relay>/<chain hash>/public/<round>`, and so is the open one whose cooldown ends first, as a half-open probe; each within 4 seconds and 16 KiB, and the whole fetch within 8 seconds, without redirects. Relays are not trusted. The keeper saves the first answer for the round it asked whose signature the pinned registry verifies with verifyBeacon, so a relay can delay an epoch and cannot change it. The relays still in flight are heard in the background for at most 4 seconds and credited: the same signature is a valid answer and another one a failure, since a signature is unique. Each relay has its own circuit. Three failures (a wrong round, a malformed or unverifiable answer, a transport error or a 5xx) open it for 120 seconds, and a valid answer closes it. An answer of not published (HTTP 425 or 404), or none within 4 seconds, counts against a relay only for a round scheduled more than two periods before the fetch's chain time: a relay may not have a newer round yet. A fetch that finds no round is retried after 2 seconds while live paid demand waits on the epoch, and otherwise backs off from 2 seconds, doubling, to 30.

Round policy. Let start be the timestamp of the epoch's start block and now the chain head's timestamp when the epoch is prepared. The epoch commits the round current at its start, floor((start − genesis) / period) + 1, while that round is at most 180 seconds old at now. Otherwise it commits the round before the latest one scheduled at now, which a relay has surely published, but never a round before the start round. The registry accepts a round up to 240 seconds old at the commit block; the keeper discards a packet older than 200, which leaves 40 seconds for the commit's own inclusion, and takes the start round only while it is 180 old, which leaves 20 for the commit to be signed. The policy is the keeper's, not the contract's.

Refresh rule. A saved beacon packet older than 200 seconds is discarded, and a current round is prepared, when no commit transaction for the epoch is in flight and the registry does not have the epoch at the latest block. A commit that is signed or submitted keeps its packet and its exact bytes, with its replacements; a published epoch keeps the packet that was published, and its work becomes committed once the finalized state has it too; the packet of a signed recipe is never replaced. A round is public and fixed by its network, so a second fetch cannot return other data for the same round. The epoch's randomness binds a target block whose hash does not exist while the packet is unpublished: a commit that was cancelled taught nobody anything about the outcome, so preparing another round after it gives the operator nothing to choose from. keeper/README.md has the exact conditions.

Availability. The drand catalog has one source and so no fallback. While no relay serves a verifiable round, no epoch is published: requests stay escrowed, cannot be proved and become refundable after expiry. Live paid demand on a beacon epoch whose fetches keep failing is reported as beacon_unavailable about 10 seconds after the first failed attempt ends (beacon_rpc_error when the keeper's own read of the chain failed, not what the relays did); the epoch_stalled health fault follows after PROGRESS_STUCK_SECONDS more (default 20 seconds), about 30 to 40 seconds after the first failure, with the EpochPreparation alert. Recovery is a new catalog: the owner schedules another source at least two epochs ahead with scheduleCatalog, and until it takes effect the current and next epoch keep their catalog. keeper/README.md has the settings and the journal tables.

### Signed API recipes

A registry registers six built-in signed API recipes itself, at initialization or, for a registry initialized before the recipe registry, in its upgrade (initializeRecipeRegistry, run as the upgradeToAndCall data). This mechanism served the epochs before the beacon catalog and stays in the contract: the registry still accepts, selects and replays these recipes. Keeper 0.4.1 and later do not prepare epochs from them, so a catalog that lists one publishes nothing for the epochs that select it (the keeper's behavior is described above); a signed catalog needs keeper 0.4.0 or earlier. The built-in recipes are:

| Recipe | Provider | Query | Exact signed record |
| --- | --- | --- | --- |
| 0 | Hyperliquid | metaAndAssetCtxs, dex "", projection symbol `/0/universe/0/name` and value `/1/0/dayNtlVlm` | `{"symbol":"BTC","value":"<decimal>"}` |
| 1 | dRPC | jsonRpc on Ethereum mainnet: eth_call of Multicall3 `0xcA11bde05977b3631167028862bE2a173976CA11` getLastBlockHash() (`0x27e86d6e`) at `latest` | `{"id":null,"jsonrpc":"2.0","result":"0x<64 lowercase hex>"}` (105 bytes) |
| 2 | TickerLayer | lastTrade, assetClass crypto, BTCUSD | `{"symbol":"BTCUSD","price":<number>,"size":<number>,"timestamp":<integer, 1 to 16 digits>}` |
| 3 | TickerLayer | lastTrade, assetClass crypto, ETHUSD | as recipe 2 with ETHUSD |
| 4 | Nodary | latestFeeds, name ETH/USD (first-party, no projection) | `{"ETH/USD":{"value":<number>,"timestamp":<13-digit milliseconds>,"category":"crypto"}}` |
| 5 | dRPC | as recipe 1 on network base | as recipe 1 |

Ids 0 to 3 keep the canonical requests of the catalog implementation that precedes the registry, so the initial catalog and every epoch committed under it select, commit and replay unchanged. The first mainnet implementation used ANU random numbers at id 1 instead of the Ethereum block hash; no epoch was ever committed from that slot on either public registry (checked on 2026-09-17: two published mainnet epochs, both recipe 2, and sixty testnet epochs from recipes 0, 2 and 3), so no published epoch needs the ANU definition to replay. Before a catalog was scheduled, slot 1 of the initial catalog paired recipe 1 with the retired provider's Airnode, which signs no Ethereum block hash, so that slot yielded no packet and fell back after 20 blocks. Evidence recorded before the registry that did use ANU replays when its definition is supplied as a recipe book entry. The Hyperliquid SOL mid and Nodary BTC/USD listings of the previous implementation are not built in; config/recipes holds recipe files for registering them. The previous ids 4 to 7 were never used by a scheduled catalog on either public registry, and the upgrade step refuses a registry that has one.

### Data templates

A template is a byte sequence of segments, each an opcode and its operands:

| Opcode | Segment | Operands | Matches |
| --- | --- | --- | --- |
| `0x01` | LITERAL | length n (1 to 128), then n bytes | exactly those bytes |
| `0x02` | HEX | n (1 to 128) | exactly n characters `0-9a-f` |
| `0x03` | DECIMAL | flags (0 to 3) | an unsigned JSON number: `0` or a nonzero digit followed by digits, then an optional fraction `.digits` when flags & 1 and an optional exponent `(e\|E)(+\|-)?digits` when flags & 2 |
| `0x04` | INTEGER | min, max (1 ≤ min ≤ max ≤ 128) | a nonzero digit followed by digits, with min to max digits |

Variable segments are greedy and never backtrack; a record is accepted only when the segments consume it exactly, so there are no trailing bytes, and it is at most 128 bytes. A well-formed template is at most 256 bytes, contains at least one variable segment and has a shortest possible match of at most 128 bytes. The segments are the smallest set that expresses every record the providers sign: literals fix key order, names and punctuation; HEX covers hashes and fixed-length random values; DECIMAL covers JSON numbers and decimal strings with the two grammar options the providers need; INTEGER covers bounded positive integers such as millisecond timestamps, which DECIMAL cannot bound. For example recipe 1's template is LITERAL(39) `{"id":null,"jsonrpc":"2.0","result":"0x`, HEX(64), LITERAL(2) `"}`, and recipe 2's is LITERAL `{"symbol":"BTCUSD","price":`, DECIMAL(3), LITERAL `,"size":`, DECIMAL(3), LITERAL `,"timestamp":`, INTEGER(1, 16), LITERAL `}`. An ANU-style array of four hex8 values is LITERAL `{"success":true,"type":"hex8","length":"4","data":["`, then HEX(16) and LITERAL `","` alternating, and LITERAL `"]}`. A beacon recipe's template is the single segment INTEGER(1, 19), the bytes `0x040113`.

The contract (contracts/libraries/DataTemplate.sol), the replay library (src/templates.ts: encodeDataTemplate, decodeDataTemplate, matchesDataTemplate) and the keeper (keeper/src/template.rs) share the verdicts in test/fixtures/epoch-data-cases.json. The built-in templates accept exactly the bytes the previous per-recipe validators accepted: test/DataTemplate.test.ts compares them against copies of those validators on every single-byte mutation of the real signed samples. A decimal is `0` or a digit sequence without a leading zero, with an optional fraction; a number is the unsigned JSON form of the same, with an optional exponent, exactly as JSON.stringify writes it (Nodary values such as `76634.54000000001` keep their binary64 digits). Records are the exact bytes above in that key order: no whitespace, extra fields, reordered keys, escaped characters, other names or symbols, uppercase hex or other lengths.

### Canonical requests and catalogs

A signed recipe's canonical request is AirnodeHub's canonical form, the JSON of [operation, canonical(parameters)] with canonical(responseProjection) appended when present, where every object at any depth becomes its [key, value] entries sorted by key and arrays keep their order; queryHash is keccak256 of its UTF-8 bytes. For example recipe 1 is `["jsonRpc",[["method","eth_call"],["network","ethereum"],["params",[[["data","0x27e86d6e"],["to","0xcA11bde05977b3631167028862bE2a173976CA11"]],"latest"]]]]` (queryHash `0xabe6d1ad9b60d0fb0a11fdb29f33b005bf366921961e833a62ba7f9c0098abda`). Keepers up to 0.4.0 read a selected recipe from the registry (cached by id), refused it unless the selection carried that recipe's canonical request and hash, the body canonicalized to it and the template was well-formed, posted the registered body byte for byte to the gateway of the slot's signer, and validated the signed record with the template before saving it. Keeper 0.4.1 and later do none of that: a signed recipe's source is refused (see Beacon epochs in the keeper) and the fallback ladder continues. SECURITY.md describes what each attestation does and does not establish.

A passthrough recipe reached a listing through the gateway's passthrough instead: the provider's own request, sent to `<gateway>/api` followed by the provider's path. Its canonical request is the gateway's passthrough request-hash preimage, the compact JSON of ["passthrough", method, path, query entries sorted by name, body as sent] with the projection entries sorted by alias appended as a sixth element, and its registered body is that same text. The method is GET without a body or POST with a JSON body; path segments, query names and projection aliases are unreserved characters, and no query name is one of the gateway's own x-airnode- parameters. The attestation arrived in the X-Airnode-Address, X-Airnode-Request-Hash, X-Airnode-Timestamp and X-Airnode-Signature response headers and signed the body exactly as received, or the projected object as compact JSON, with the digest and signature rules of a posted body, so the registry accepts passthrough recipes as they are. The gateway signed a listing under different request hashes in the two forms, so a listing's passthrough form is a separate recipe. The replay library's PASSTHROUGH_EPOCH_REQUESTS and passthroughEpochRecipe give the passthrough form of each built-in recipe, which answers with the same record and keeps its template; config/recipes/passthrough-*.json hold registration files for the rollout catalog's five with real signed samples. For example the passthrough form of recipe 4 is `["passthrough","GET","/feed/latest",[["name","ETH/USD"]],""]`.

A registry starts with its initial catalog: recipes 0, 1, 2 and 3 with the four signers given at initialization, hashed as keccak256(abi.encode(RECIPE_DOMAIN, address[4] signers)) and bound into protocolConfigurationHash; catalogHash() and the getters hyperliquidSigner, ethereumBlockSigner, btcTradeSigner and ethTradeSigner keep it. The owner replaces it for future epochs with scheduleCatalog(recipes, signers, fromEpoch): 1 to 10 distinct registered recipe ids with nonzero signers in slot order, for an epoch at least two ahead of the current one; a still-pending version is replaced and an active one never is. Its hash is keccak256(abi.encode(RECIPE_DOMAIN, uint8[] recipes, address[] signers)), and it emits CatalogScheduled(fromEpoch, catalogHash, recipes, signers). catalogAt(epochId) returns the hash, recipes and signers an epoch selects and commits with, and Epoch.catalogHash records that hash, so the current and next epoch, prepared snapshots and open requests never change catalog. A signed catalog can interleave providers, as [0, 1, 2, 4, 5] does with each provider's Airnode (Hyperliquid, dRPC, TickerLayer, Nodary, dRPC): neighbouring slots, including the last and the first, never share a signer, so every fallback moves to another provider. A beacon's signer is its slotSigner, which scheduleCatalog enforces. Both networks run the drand catalog [11] with the signer slotSigner(11): one source and no fallback (Arc Testnet from epoch 11319, Arc Mainnet from epoch 12448).

Raw signed data is at most 128 bytes; it is never cropped. Low-s 65-byte EIP-191 signatures bind the canonical query, signed timestamp and exact data. At publication the signed timestamp cannot be in the future or older than 240 seconds (MAX_ATTESTATION_AGE; the keeper stops sending a saved packet at the same age and replaces a beacon round at 200 seconds). A keeper up to 0.4.0 reconstructed object envelopes with round-trip binary64 parsing and ECMAScript number formatting, and left raw string envelopes and passthrough bodies unchanged. A beacon round is instead its number in decimal with a 64-byte BLS signature (see Beacon recipes).

Equal provider data across epochs is allowed. Epoch parameters produce distinct commitments; hashing repeated data is not a claim of fresh independent entropy. If the first saved signed response becomes stale, it cannot be refreshed to rescue a request; a beacon round that stales before its epoch is published is replaced (see the refresh rule). The unfulfilled request retains its refund path.

## Proof and settlement

The VRF seed binds chain ID, coordinator proxy, key hash, request ID, consumer, client seed, mapping hash, request block, resolved target block/hash, epoch ID and epoch hash. Fulfillment submits only request ID plus real VRF proof: 452 calldata bytes. The non-indexed FulfillmentEvidence packet is 416 bytes. fulfillRandomnessBatch accepts up to 16 request/proof pairs and runs each exactly like fulfillRandomness (same events, evidence, settlement and callback); members already fulfilled, refunded or expired are skipped with FulfillmentSkipped(requestId, reason: 1 fulfilled, 2 refunded, 3 expired), and any proof or readiness failure reverts the whole batch. Before serving any member, the batch requires gas for every member it will serve (140,000 + Σ(callbackGasLimit + callbackGasLimit/63 + 400,000)) and otherwise reverts with InsufficientCallbackGas, so no callback can revert the batch after an earlier member's result was revealed. EpochCommitted separately archives the full canonical query and the packet, a signed API record or a beacon round, once.

Valid proof acceptance at or before the request deadline earns the fee, including when its callback fails. Each request stores the fee it escrowed (requestFeePaid); keeper share, treasury share and refund all settle from that stored amount, never from the live fee, so a later fee change cannot alter what an open request pays or refunds. A configured basis-point share is paid to the wallet that submitted the accepted proof when the registry authorizes it to publish epochs (isAuthorizedCommitter: the current committer or an allowed backup committer), and to committer() for any other submitter, so an arbitrary submitter is never paid. A registry that does not answer that view, or whose call reverts, also pays committer(). Failed keeper transfers become backed keeper credits. The remainder becomes treasury earnedFees. Neither path spends pending-request escrow or refund credits. Callback retries keep the same result and never pay another keeper share. Expired unfulfilled requests remain refundable to their original recipient by transaction: the refund is feePaid × refundBps / 10000 using the ratio snapshotted into the request at creation (requestRefundBps; owner-set between 5,000 and 10,000 bps for future requests, default 10,000) and the remainder becomes earnedFees.

## Administration and verification

EpochEntropy and D20VRFCoordinator run behind atomically initialized ERC1967 proxies with owner-authorized UUPS upgrades. Ownership transfers require acceptance by the proposed owner. The registry owner can rotate the committer and allow up to four backup committers (setBackupCommitter, BackupCommitterSet, isBackupCommitter), which may publish epochs under exactly the committer's rules and are paid the keeper share of the requests whose accepted proofs they submit themselves (isAuthorizedCommitter), while any other submitter's fulfillment pays committer(); coordinator owner can change fee recipient, keeper share, pricing (setPricing, bounded to minFee at most 10 native units, multiplier 0–20 and overhead 100,000–2,000,000 gas) and the expiry refund ratio (setRefundBps, never below 50%). The registry owner can also register recipes and beacons, which are append-only and never edited, and schedule catalogs, which apply only to future epochs and are never rewritten for a current or published one. This implementation has no VRF-key or request-input setter. Upgrade authority can change code, so it is a trust assumption, not an immutable guarantee against governance.

Replay uses the initialized configuration, including initialFeeRecipient and initialMinFee rather than the mutable payout address and live pricing. Verify trusted chain/receipt data, source anchor, the fallback attempt implied by the committed source and its window (publication block at least start+attempt×20), request block, actual publication block/time, target=max(requestBlock,commitBlock+1), signatures and recipes (with the catalog in force for that epoch, from catalogAt, or CatalogScheduled events and the initial catalog, and each selected recipe's definition, from getRecipe or RecipeRegistered events), VRF and transcript. The replay library's resolveEpochCatalog turns a catalogAt view into the catalog replay expects and recognizes the initial catalog by its hash; its recipeBook defaults to the built-in recipes, and readEpochRecipes reads any other registered recipe, checked against its query hash. For a beacon epoch replayEpochCommitment checks the round's number, its scheduled time and its BLS signature under the registered key (verifyBeaconRound in src/beacon.ts, the same computation as D20BeaconVerifier) and that the catalog's signer is the registration's slotSigner; readEpochRecipes reads a beacon recipe's registration with beaconOf, and a recipe book entry carries it. Replay does not run the registered verifier, so its address and runtime code are chain context to check against the reviewed D20BeaconVerifier. Epochs published before the beacon catalog took effect are signed API records and verify as such, with the recipes and catalog in force for them. Resolve the implementation history of both proxies for the relevant transactions; proxy addresses/code alone do not identify execution logic. The current protocol has one packet schema; no alternate decoder modes are included.

The keeper pins both proxy implementation addresses/runtime hashes in addition to proxy/configuration identity and fails closed on unreviewed changes. Upgrade operations require storage-layout review and request/epoch/fee/replay regression tests. Current local layout baselines are in storage-layout/.

### Changing recipes and catalogs

Registering a signed API listing is a registration, not an upgrade (admin.ts register-recipe checks a recipe file's body, template, signer and a signed sample first), but keeper 0.4.1 and later do not prepare epochs from signed recipes, so a catalog that lists one publishes nothing for the epochs that select it. Recipes are never edited or removed, so a changed listing becomes a new id and older epochs keep replaying with the recipe they used. A new source is a drand network, registered as below.

Adding a beacon also needs a verifier contract. Deploy D20BeaconVerifier (create2-deploy.ts beacon-verifier: no constructor arguments, so one salt gives the same address on every chain), then run admin.ts register-beacon. It requires the verifier's runtime code to equal the freshly compiled contract, fetches a sample round from a relay it does not trust, verifies the round locally and through the verifier, refuses a beacon that is already registered, simulates the call and prints the registration, its slotSigner and the manifest fields to record. schedule-catalog then lists the recipe with the slotSigner it reads from the registry, which accepts no other. Keepers need a release with beacon support (0.4.0 or later) and reachable relays, nothing else. A keeper without that release records a beacon source as failed and, with one source, publishes nothing, so every keeper that can publish, the primary and each follower, must run it before a beacon catalog is scheduled. A catalog of signed recipes would need keeper 0.4.0 or earlier again, since 0.4.1 does not prepare them. The upgrade of a live registry and its Safe batches are in [the registry upgrade runbook](registry-upgrade.md#beacon-upgrade).

The upgrade that introduced the registry replaces the hardcoded recipes of 640b60c (Arc Mainnet) and 96cc722 (Arc Testnet). Its storage keeps every declared slot of both layouts: slot 8 (640b60c's empty four-signer catalog array, 96cc722's retired uint256, zero on both registries) stays reserved, slot 9 holds the catalog array (unused gap on 640b60c, empty on 96cc722), and the gap gives up three slots: the recipe array takes slot 10, the backup committer mapping slot 11 and its count slot 12, so the gap shrinks from 38 to 35 and the layout still ends at slot 47. The upgrade call data runs initializeRecipeRegistry, which registers the built-in recipes once (reinitializer 2, owner-only) and refuses a registry with a non-empty slot 8 or a scheduled catalog, whose recipe ids would change meaning. Until the owner scheduled a catalog, epochs kept the initial catalog: its slot 1 paired recipe 1 with the initial signer, which on both public registries is the retired provider's Airnode, so a slot 1 selection yielded no valid packet and fell back to the next slot after 20 blocks. The initial catalog, catalogHash() and protocolConfigurationHash do not change. No epoch on either public registry was committed from slot 1, so the current replay library verifies all of their published epochs; other deployments must replay each epoch with the recipes of the implementation active when it was committed. The rollout steps are in [the registry upgrade runbook](registry-upgrade.md).

The beacon upgrade replaces the registry implementation again, with upgradeToAndCall(implementation, 0x) and no initializer. Its storage takes slot 13 from the gap, which shrinks from 35 to 34 slots with the layout still ending at slot 47: the beacons mapping from recipe id to registration. Every other slot, view, recipe, catalog and published epoch stays as it was, the coordinator is not upgraded, and the signed-recipe code stays in the contract. Registering the beacon and scheduling its catalog are separate owner calls. test/Upgradeability.test.ts upgrades a registry running the recorded live bytecode with no call data and compares every slot and view, then registers a beacon, serves a request from a beacon epoch and replays the history. The steps are in [the registry upgrade runbook](registry-upgrade.md#beacon-upgrade).
