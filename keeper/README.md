# d20dao keeper

Release notes: [CHANGELOG.md](CHANGELOG.md). Version 0.5 adds Robinhood Chain (round mode, soft finality, the Arbitrum gas model); an Arc keeper behaves as 0.4.1 did.

The service prepares the drand round of each epoch locally and settles paid randomness requests through one SQLite WAL/FULL transaction journal. It opens no incoming application port. The public verifier is separate and uses chain evidence, not private keeper storage.

## Request processing

Each 200-block epoch selects one source of its catalog (1 to 10 registered recipes with their signers; see ../docs/epoch-protocol.md) using the epochStart-1 block hash. The keeper records the epoch's source count from the registry (`sourceCountAt`) with its work and walks at most that many fallback attempts. It reads the selected recipe from the registry (`getRecipe`, cached by id because recipes never change) and prepares an epoch only from a drand beacon recipe (below): the selection must carry that recipe's canonical request and query hash, and the beacon's registration, request, body and data template must agree. A recipe that fails that check is recorded as that source's permanent failure, so the fallback ladder continues. The first verified round is saved once. At most one background fetch runs, bounded to 8 seconds. Eight seconds is below one 20-block fallback window (about 10 seconds on Arc): a slower fetch could not win that window and would only hold the fetch slot past the moment the next source may be tried. No source switching or replacement of a persisted packet is allowed (a stale beacon packet is the one exception, see below).

Idle snapshots stay local. A live paid request can escrow before publication; only then does the keeper publish the epoch packet. The VRF target is max(requestBlock,commitBlock+1). Requests share a published epoch but retain distinct inputs and proofs. No unfulfilled request is served after its 60-second deadline.

Discovery rescans pending request IDs, including gaps missed during reboot. Accepted proof and signed transaction bytes are journaled before broadcast. Receipt reconciliation, identical-byte retries, fee replacements and cancellation preserve nonce ownership. Unknown consumed nonces fail closed. A slow relay fetch is outside the transaction path; bounded maintenance preflight yields so existing work can proceed.

Prepared requests are sent in batches so one nonce serves many requests. Each send pass takes the earliest-deadline prepared requests, skips any that are terminal or within SEND_MARGIN_SECONDS of their deadline, and, when at least two qualify, estimates one `fulfillRandomnessBatch` of up to FULFILL_BATCH_MAX members (default 8, allowed 1–16; 1 keeps the single-request path only). No fulfillment's gas limit falls below its floor: the budget the coordinator's batch guard requires for its members (140,000 plus, for each member, its callbackGasLimit, that limit / 63 and 400,000) and a bound on the transaction's own cost around it (73,112 plus 27,168 per member, for intrinsic gas, calldata, dispatch and the guard's reads of each member), grown by a 63rd because the coordinator's proxy passes on only 63/64 of the gas it has left (EIP-150). eth_estimateGas sees a callback only as expensive as it chooses to be in the simulation (Arc simulates with a zero gas price), and a callback can read the results of earlier members of the same batch, so a callback that burned its whole limit only on chain could otherwise leave a later member short of the coordinator's per-member gas check and revert the whole batch. With the floor every member can burn its whole callback and the next still passes its check, on the guarded coordinator and on one without the guard, and an estimate that comes back short cannot make the guard revert. The guarded coordinator's estimate already contains the budget, so the estimate is padded only by a fifth of what it holds beyond the budget, and at least 50,000. A single fulfillment follows the same rule. Before a batch is estimated it keeps the earliest members whose floor fits MAX_GAS and MAX_TX_COST_WEI at the current price. A batch still over a cap after its estimate is shrunk to the members that fit and re-estimated, and a batch estimate the node refuses without a revert (a gas limit it does not estimate) is halved; after at most four shrinks the single path takes over, and no batch is sent below its floor. A price above MAX_FEE_PER_GAS_WEI is a budget deferral before any estimate. A batch preflight that reverts falls back to single sends for that pass, and a request whose own single preflight the node rejects keeps its single retries but is left out of later batches, so one bad proof cannot hold the others at single-lane speed. The batch is signed and journaled with its member list (`batch_members`) under one nonce before broadcast; a request is never live in two nonces. Members that become fulfilled, refunded or expired while the batch is pending are skipped on chain (`FulfillmentSkipped`), so the batch is rebroadcast and fee-bumped while any member is still live and timely, and its nonce is cancelled once none is. A finalized receipt resolves every member from that member's own chain state in one journal transaction. A batch that reverts returns its still-live members to `prepared` in that same transaction, leaves them out of later batches and resends them one at a time, ahead of the next batch, each on its own nonce; the proofs are public by then and the results fixed by the VRF, so a resend reveals nothing new. Only a request whose own single attempt reverts is blocked. Telegram and Discord notices name only the members the receipt actually served.

## Configuration and identity

Discovery reads a fixed finalized block. Receipts resolve the nonce only after finalized canonical inclusion; a durable checkpoint detects reversed finalized history and stops processing. When the finalized nonce is used but the endpoint that answered first serves no receipt, every endpoint is asked for it before the nonce resolves from contract state alone, so an endpoint that has not caught up with a block does not cost the receipt's log line and notices. Arc's deterministic finality, on Arc Mainnet and Arc Testnet alike, is the approved profile. Other networks need an explicit finality review against the 60-second window; see [finality and recovery](../docs/finality.md).

Preparation attempts use a persisted fair queue with a 250 ms minimum retry interval. A request's proof input is read only once the finalized head has reached its target block plus the coordinator's confirmationBlocks; earlier the coordinator reverts that read on every endpoint. A blocked source or target cannot monopolize the first preparation batch after restart.

Each preparation pass has a time slice of 15% of the configured tick budget (3 seconds with the default 20-second tick). At the slice it yields only when that pass has journaled a proof and the nonce lane can send; journaled proofs remain when slow peers are cancelled, and the sender runs before the next pass. Without a journaled proof, cancelling would gain nothing and uniformly slow RPC could discard every pass, so the pass continues to a hard cap of 35% of the tick budget, never past 80% of the tick. A pass that reaches its cap without a proof skips the second pass of that tick. At most four blocking proof computations remain active even after cancellation. The single unresolved nonce lane is unchanged.

Runtime identity checks read both implementation slots and all four runtime codes in one JSON-RPC batch from one endpoint (a moved slot whose proxy has an approved next implementation costs one more read of the new code, from the same endpoint), with an 800 ms per-endpoint attempt and a 2.4-second total read budget inside the existing 3-second check. Reads are hedged: when an attempt has no response after its attempt budget, the next endpoint starts while the earlier attempt keeps running, and the first success wins inside the total budget. An endpoint slower than 800 ms can therefore still pass in any position, and a single configured RPC is attempted for the full 2.4 seconds. Hedge timers alone start at most three endpoints within 2.4 seconds; a failed attempt starts the next endpoint immediately. An attempt that fails, or is still unanswered, after a full attempt budget cools that endpoint for five seconds and advances the shared preferred endpoint; successful endpoints become preferred. Cooling endpoints are tried last rather than skipped. Other reads use the same hedging with their existing 8-second per-endpoint budget. Hedging applies only to reads. Broadcast is still a single attempt, followed by receipt reconciliation rather than automatic multi-endpoint resubmission. More `RPC_URLS` entries provide failover, not automatic load balancing or a measured throughput guarantee.

A well-formed request answered with something the read cannot use is that endpoint's failure, not a result: a body that is not JSON-RPC, a null block (an endpoint that does not serve the `finalized` tag answers that way), a quantity that is not `0x` and 1 to 64 hex digits, a block without `baseFeePerGas`, a storage word that is not 32 bytes, a receipt without the fields reconciliation reads, or call data that does not decode. Typed reads check that shape inside the read, so the endpoint is cooled at once like a slow one and the next endpoint answers the whole read, a batch and the pin check's follow-up read included. The read fails only when every endpoint has failed, as an RPC failure that counts toward MAX_TICK_FAILURES. A well-formed answer is judged only after the read and never retried elsewhere: an endpoint that contradicts a pin or the finalized checkpoint still fails the tick. At startup an endpoint that does not answer, rate limits or answers unusably, in the chain and code probe or in its own pin check, is left out and the keeper starts on the others; a well-formed answer for another chain, other coordinator code or other pins still fails startup.

An HTTP 429, or a provider error whose code or wording says the request rate was exceeded, puts that endpoint into a jittered back-off (1 s doubling to 30 s) during which reads skip it, and reads move to the other endpoints. A tick that cannot run only because every endpoint is rate limiting is deferred with the same back-off: it does not count toward MAX_TICK_FAILURES, health reports `rpc_rate_limited` until a tick runs again, and startup waits instead of exiting. A round keeper (`COORDINATOR_KIND=round`) also defers, with the same back-off and without counting it, a tick that failed only because the endpoints answered with transport or provider errors (HTTP 429 or 5xx, a rate limit, JSON-RPC -32000, no answer in time); health reports `rpc_unavailable` once such ticks have gone on for PROGRESS_STUCK_SECONDS, until a tick runs again. Anything else still counts, including a pin, chain or configuration mismatch and a failed send, and so does every other failure of an epoch keeper.

An endpoint that refuses a JSON-RPC batch for its size (an HTTP error or a JSON-RPC error that names batches, or HTTP 400 or 413, as a free plan answers a batch of more than three) is asked the same calls again at once in chunks of half the size, halving down to single calls. The chunk size it answered is kept for that endpoint for the life of the process, and the refusal is neither a failure of the endpoint nor a cooldown; only a chunk that fails as anything else fails the read there. A rate limit is never taken for a refusal.

A fetch of a beacon round that finds none is retried with a 2 to 30 second back-off (below); a source whose recipe the keeper refuses is a permanent failure that blocks that source only. Once a source has failed without a packet, the keeper moves to the next fallback source when its window opens (20 blocks per attempt into the epoch; see docs/epoch-protocol.md), logging `Epoch source produced no packet; moving to the next source`, and publishes it with `commitEpochFallback`. The last source keeps retrying or stays blocked. An authenticated saved packet is never replaced, except for the stale beacon packets described below. Old-epoch retries require still-live demand and expired requests remain unserved.

Signed API recipes are not supported since 0.4.1. A catalog that selects a recipe that is not a drand beacon, such as a signed API recipe, does not stop the keeper and is never retried: the keeper logs an error that ends with `signed API recipes are not supported since 0.4.1` and names the epoch key and the recipe, records that source as failed for good (so the fallback ladder moves on at the next window), reports the health fault `epoch_recipe_unsupported:<recipe id>` and prepares the epochs after it as usual. The fault is written at once and stands until an epoch's selected source is supported again, so it shows with no request waiting. It clears when a later poll finds a supported selected source, so a catalog that mixes beacon and signed recipes can make it come and go; schedule beacon-only catalogs. Requests of epochs the registry already published are fulfilled as always. A request that waits on an epoch that cannot be prepared stays escrowed and is refundable after expiry, and the live paid demand on that epoch is the `epoch_stalled` fault with the reason `unsupported_recipe`. Both live networks run the single drand recipe `[11]`, so this protects a keeper from a catalog scheduled by mistake; the epochs published from signed API records before it verify as before.

Each tick also checks whether live paid demand depends on epoch work that is blocked with no fallback source left (reason `blocked`, or `unsupported_recipe` when its recipe is not a drand beacon) or blocked with a saved packet that cannot be sent, or on a saved packet already older than the attestation freshness bound at the finalized head, or on a beacon epoch whose fetches have kept failing for 10 seconds, the last failure at most 15 seconds ago (reason `beacon_unavailable`, or `beacon_rpc_error` when the last failure was the keeper's own read of the chain, not what the relays did; see below). Such demand cannot be served: the keeper records the `epoch` health observation, which starts about 10 seconds after the first failed attempt ends, and the `epoch_stalled` fault follows after PROGRESS_STUCK_SECONDS more (default 20 seconds), about 30 to 40 seconds after the first failure. It logs the epoch key and reason once per episode, and pushes the Telegram `EpochPreparation` alert under its cooldown. The observation clears as soon as no such demand remains, whether because the epoch was published or because the demand expired. The freshness bound and the immutability of a saved packet are unchanged, except that a stale beacon packet with no commit in flight, for an epoch the registry does not have, is refreshed and never counts as stale or blocked.

The binary reads process environment; it does not implicitly load a dotenv file. See .env.example. CHAIN_ID is explicit. RPC_URLS, COORDINATOR_ADDRESS, KEEPER_DB, TX_KEY_FILE and VRF_KEY_FILE are chain-neutral settings. The transaction key and VRF key must differ. KEEPER_DB must be absolute.

Removed settings. `EPOCH_API_ENDPOINTS`, which releases up to 0.4.0 read to choose a gateway for each Airnode, is not read any more. A keeper environment that still sets it, with any value, starts normally and logs one warning that names it (`EPOCH_API_ENDPOINTS is ignored: signed API recipes are not supported since 0.4.1, and epoch rounds are read from DRAND_RELAYS; remove it from the keeper environment`); it never refuses to start because of it. `TEST_API_BASE` remains local-chain-only and names the one relay a test chain reads rounds from (`<base>/<chain hash>/public/<round>`), replacing `DRAND_RELAYS`.

A beacon recipe (registered with `registerBeacon`, see ../docs/epoch-protocol.md) names a drand network: its canonical request and body are `["drand","0x<chain hash>"]` and its data template is a round number. The keeper reads `beaconOf` only for recipes whose canonical request starts with `["drand","` (an older registry has no `beaconOf` and cannot hold one; if the call reverts for a drand recipe on the source's second attempt or later, that source fails for good and a catalog with another source falls back to it) and fetches only a consistent registration: a verifier, a schedule with a period under 200 seconds (longer rounds would go stale before they could be committed), the canonical request and body of its chain hash and the round template. An inconsistent one is refused, like any recipe that is not a consistent beacon. Rounds come from `DRAND_RELAYS`, at most 8 comma-separated relay base URLs, HTTPS without credentials, query or fragment and each at most once (default `https://api.drand.sh`, `https://api2.drand.sh`, `https://api3.drand.sh` and `https://drand.cloudflare.com`; the startup log lists them; loopback `http://127.0.0.1` relays are accepted on chain 31337 only). Every relay whose circuit is closed is asked at once for `<relay>/<chain hash>/public/<round>`, and so is the open one whose cooldown ends first, as a half-open probe; each within 4 seconds and 16 KiB, and the whole fetch within 8 seconds. Relays are not trusted: the first answer for the round asked whose signature is 64 bytes of hex and which the pinned registry itself verifies (`verifyBeacon`, an `eth_call`) is saved, so a relay can delay an epoch but not change it; relays that give the same signature cost the registry one call. The relays still in flight are heard in the background for at most 4 seconds after the fetch began, and never hold the fetch or a shutdown: the same signature counts as a valid answer, another one as a failure (a signature is unique, so the registry is not asked again). A wrong round, malformed answer, signature that does not verify, transport error or 5xx counts against that relay's circuit in the journal's `epoch_relay_breaker` table (three failures open it for 120 seconds, and a valid answer closes it, the probe's too). HTTP 425 or 404, or no answer within 4 seconds, counts against a relay only when the round was scheduled more than two periods before the chain time of the fetch: a relay may not have a newer round yet, and holds a request for the next one for about 2 seconds. For an older round it is a failure (`round already due but not served`). A fetch that finds no round is retried after 2 seconds while live paid demand waits on the epoch, and otherwise after a back-off from 2 seconds, doubling, to 30 (demand that arrives during the back-off is retried 2 seconds after the last failure); the first failed fetch of an epoch is logged at warn, the repeats at debug and one for every 5 minutes it goes on at warn, and the message names each relay and its reason. A fetch that failed on the keeper's own reads of the chain (the start block, or the registry's verdict on a signature) does not blame the relay whose signature could not be checked, is retried in the same way and is reported as `beacon_rpc_error`. The round is the one current at the epoch's start block, `floor((start time - genesis) / period) + 1`, as long as it is at most 180 seconds old at the chain head when the epoch is prepared (the 20 seconds that remain of the 200 a packet may age are for its commit); otherwise it is the latest scheduled round minus one, which a relay has surely published, and never a round before the start round. The attestation is the round's scheduled time, the round in decimal and the relay's 64 signature bytes. TEST_API_BASE replaces the relay list by that one base. The journal's `epoch_work` gains three nullable columns for the run of failed fetches, `failing_since`, `failed_at` and `failed_rpc`; a failure more than 15 seconds after the one before starts a new run.

Every keeper that can publish, the primary and each follower, must run 0.4.0 or later before a catalog that lists a beacon is scheduled: 0.3.0 refuses beacon recipes, so its epochs block and their requests are refunded. Release 0.4.1 removed the signed API source, so a catalog of signed recipes needs keeper 0.4.0 or earlier again. Journals are compatible both ways. 0.4.1 changes no table or column and drops none, so it opens a journal that 0.4.0 used as it is, with no migration. The `epoch_breaker` table of the Airnode gateway circuits stays in it, unread. A signed packet that 0.4.0 saved is handed to the sender as saved when live paid demand waits on its epoch. Work that 0.4.0 left unfinished for a signed source is not fetched again: if its epoch is still being prepared it is refused as an unsupported recipe (above), and otherwise it is retired after 50 epochs like any unused work, without an error. 0.4.0 opens a journal that 0.4.1 used (it creates `epoch_breaker` itself when it is missing). The journal also stays readable by 0.3.0: the added `epoch_work` columns are nullable and the `epoch_relay_breaker` table is one 0.3.0 does not read.

A saved beacon packet is the one exception to a saved packet being final. When a commit would be signed for a beacon packet older than 200 seconds, or live paid demand waits on such a packet in blocked work, the keeper discards the packet and prepares a current round (`Saved beacon packet is too old, its epoch is unpublished and no commit for it is in flight; discarded`) instead of blocking the epoch. It does so only while all of these hold: the work is `pending`, `prepared` or `blocked`; every transaction the journal holds for the epoch is resolved, or there is none, so a commit that was cancelled, replaced by a cancellation or mined and reverted no longer holds the packet once its nonce has resolved; and the registry does not have the epoch at the latest block (`getEpoch` has a zero `epochHash`, read immediately before the discard). The discard is a compare-and-swap in the journal on the exact saved packet and selection and on the absence of any transaction that is not resolved. A commit that is signed or submitted, with its replacements, keeps its packet and its exact bytes; a published epoch keeps the packet that was published, and its work becomes `committed` once the finalized state has the epoch too; and a packet that an earlier release prepared for a signed recipe is never replaced. A commit cancelled at the 240-second bound resolves its epoch to `blocked`, and the keeper checks blocked work that a request waits on at every tick. A round is public and fixed by its network and the epoch's randomness still binds a target block that does not exist when the packet is committed, so holding the packet back protects nothing, and a commit that was signed and then cancelled taught nobody anything about the outcome.

For nonlocal chains, pin EXPECTED_CODE_HASH, EXPECTED_PROTOCOL_HASH, EXPECTED_IMPLEMENTATION_CODE_HASH and EXPECTED_REGISTRY_IMPLEMENTATION_CODE_HASH. Both proxy implementation slots and runtime code are checked at startup and immediately before every signature and broadcast; without a send they are checked again at the next tick after an `Upgraded` event and at least every 15 seconds (every 120 seconds for a round keeper with nothing open and a live subscription; see Polling and subscriptions). An unreviewed upgrade stops sends. A primary's transaction wallet must be the registry's current committer and a follower's must be one of its allowed backup committers; a wallet that loses that authorization keeps reconciling but stops sending. After a reviewed registry upgrade (for example the recipe registry, see ../docs/registry-upgrade.md), run the keeper image built for that implementation, set EXPECTED_REGISTRY_IMPLEMENTATION_CODE_HASH to its runtime hash and restart; sends resume once the pins match.

An in-place upgrade can be approved ahead of time. APPROVED_NEXT_IMPLEMENTATION_CODE_HASH (coordinator) and APPROVED_NEXT_REGISTRY_IMPLEMENTATION_CODE_HASH (registry) name the runtime code hash of a reviewed next implementation; they are separate from the pins, empty approves nothing and a zero hash is refused. Startup accepts a proxy whose implementation code hash is its pin or its approved next hash; the proxy code pin, the protocol configuration hash, the VRF key, the committer and every other startup check are unchanged. When a running keeper sees a proxy move to an implementation with its approved next hash, the proxy code unchanged, it signs and sends nothing more and exits at once with status 75, without failed ticks or error notices; the process restart (Docker's restart policy, or a supervisor that restarts on a non-zero status) runs every startup check against the new implementation. Pins never change inside a running process, and a tick interrupted this way leaves the journal as any interrupted tick does, for the restart to reconcile. The first start on the new implementation logs it and, with Telegram configured, sends an informational notice; every start on it warns until its hash is the pin; the approval can then be removed. While the new implementation reaches the configured RPC endpoints at different times, startup tries again for up to ten seconds instead of mixing their views. Any other implementation change fails as before: ticks fail, the keeper exits after MAX_TICK_FAILURES and startup refuses it. Settings are read only at startup, so set the approval and restart the keeper before the upgrade (a Docker container keeps the environment it was created with until it is recreated). A keeper release without these settings ignores them.

SEND_TRANSACTIONS defaults false. Consumer requests are public; no allowlist setting is required. Fee/cost ceilings and the SEND_MARGIN_SECONDS budget are enforced rather than bypassed to meet a deadline. The keeper needs an initial gas balance; accepted proofs then pay it the configured share of earned fees. Failed transfers become keeper credits. No pending refund escrow funds keeper operations.

Every fulfillment, epoch publication and replacement prices gas at twice the observed base fee plus a priority fee: the median tip of the last 20 blocks, clamped to MIN_PRIORITY_FEE_WEI and MAX_PRIORITY_FEE_WEI (1 and 50 gwei by default), with the minimum used when fee history is unavailable. Replacements outbid the previous attempt by 12.5% and never tip below the current median. Fulfillments also pay for themselves: with FEE_COVERAGE_BPS (default 10000) a single or batched fulfillment is sent only when the escrowed fees of its requests (requestFeePaid) cover the expected cost at the observed base fee and tip. A batch drops its lowest-fee member until it is covered; uncovered requests stay prepared and are refunded if they expire, so the operator caps act as circuit breakers rather than pricing. Epoch publication is not fee-gated because every request in the epoch depends on it. A send is deferred when that price exceeds MAX_FEE_PER_GAS_WEI (CANCEL_MAX_FEE_PER_GAS_WEI for nonce cancellations), when price times gas exceeds MAX_TX_COST_WEI, or when the gas limit (never below the floor, as above) exceeds MAX_GAS. MAX_GAS defaults to 3,000,000, which carries one request with the coordinator's largest callback gas limit. A budget deferral is distinguished from chain or RPC deferrals: it logs the cap to raise with the required amount, pushes the Telegram `FeeBudget` alert, and records a `fee_budget` health observation that becomes the `fee_budget_exceeded` fault after PROGRESS_STUCK_SECONDS; it does not also record the settlement stage, because the send is forbidden by configuration rather than allowed work without progress. The observation clears at the next affordable signed transaction or at startup: caps reload only through a restart, so it describes the previous configuration, and the next deferral under the reloaded caps re-raises it. Expiry alone does not clear it. Startup and the 60-second Telegram status observer additionally warn when the observed base fee already prices sends above MAX_FEE_PER_GAS_WEI. The defaults in .env.example are conservative testnet values; the same file documents the Arc mainnet values (chain 5042, `arc-mainnet` in ../chains.json): MAX_GAS 6,000,000, MAX_FEE_PER_GAS_WEI 2000 gwei, CANCEL_MAX_FEE_PER_GAS_WEI 2500 gwei and MAX_TX_COST_WEI 4 native USDC for base fees observed at 176–251 gwei.

## Primary and follower keepers

A second keeper can take over automatically while the primary is down, without a shared database, lease or coordination service: the chain arbitrates between the two wallets. The primary runs with `KEEPER_ROLE=primary` (the default) and its transaction wallet must be the registry's `committer()`. A follower runs with `KEEPER_ROLE=follower` on another host, with its own transaction wallet, journal and host-local scope locks, and the same VRF key, because the coordinator verifies every proof against its one key. Its wallet must be an allowed backup committer (`setBackupCommitter(wallet, true)`, see ../docs/registry-upgrade.md) and must not be `committer()`. Startup checks this, and ticks check it again at once after a committer or backup-committer event, every 2 seconds while work is open and every 30 seconds otherwise. A wallet that simply does not have the right, because the owner has not granted it yet or has revoked it, disables sending: the keeper keeps running, keeps reconciling the transactions it already signed, reports `wallet_unauthorized` as a health fault and sends a notice, and resumes by itself if the owner grants the right again. A wallet holding the other role's key, a follower running the committer's key or the reverse, is refused outright, at startup and on the tick, because no owner action makes that run correctly. With Docker, a host can run followers for several networks as named instances with separate settings, journals, keys and images (../deploy/docker/README.md, "Several keepers on one host").

The follower discovers requests and fetches epoch packets exactly like the primary, and prepares proofs from the newest end of the queue, the end it sends from; it sends a fulfillment only for a request the join rule below has released to it, and it publishes an epoch attempt only while live paid demand exists and the attempt is still unpublished `FOLLOWER_DELAY_SECONDS` after the later of its fallback window opening and the first demand this node saw for it. The primary never waits. When the follower takes over it logs `Follower published epoch E` and `Follower served request N` and sends the same notices to Telegram.

The two keepers stay out of each other's way by working the queue from opposite ends rather than by waiting for each other. The primary serves the oldest deadline first. A follower joins the queue only when the join rule fires, and then works the newest end backwards, so the fronts meet only when the queue is exhausted. The rule, evaluated once per tick from state the follower can see on chain:

- the oldest unserved request is older than `FOLLOWER_DELAY_SECONDS` (5 to 30, default 20), or
- the visible unserved queue is deeper than `FOLLOWER_QUEUE_JOIN` (default 150), which is the burst size a single lane cannot clear within the deadline, or
- the primary is chain-dead: work this follower could send has been waiting `PRIMARY_LIVENESS_SECONDS` (5 to 30, default 10) while `committer()`'s confirmed nonce, read at the same finalized block as the timestamps, has not advanced.

A joined follower leaves again only once the queue is both shorter than 32 requests and younger than 10 seconds, so it does not drop out in the middle of a burst. Independently of role, lane and join state, every node sends a request that comes within 20 seconds of its deadline: that is the last line before a refund, and the configuration check keeps `SEND_MARGIN_SECONDS` and a fulfillment round inside it. An idle primary is never called dead, because nothing was waiting; a stuck primary, whose nonce stops while work waits, is, so a takeover starts within the liveness window. Pending requests on a beacon epoch that this follower has no packet for, because its own fetches keep failing, are not work it could send: with drand out of reach a silent primary says nothing. Prepared ones are, since their epoch is published, and so are pending ones once it has the packet, so it takes over when only the primary cannot reach drand. Nor are pending requests on an epoch whose selected source was refused as an unsupported recipe (above): every keeper of this release refuses it, so a silent primary says nothing there either; a prepared one still is work, whoever published its epoch. A restarted follower has no observation yet and cannot declare death until it has watched for a whole window, so a rolling restart never causes an early takeover, while the safety age still protects anything close to its deadline.

The default liveness window follows the measured behaviour of a working primary: at most about 3 seconds between batch transactions under load, and about 6 seconds for an idle epoch's publish-then-serve pipeline. With more than one follower, `FOLLOWER_LANES` (1 to 4, the registry's backup-committer limit) and `FOLLOWER_RANK` split the tail by request id (`id % lanes == rank`), deterministically and without any coordination between the followers. Epoch publication keeps the plain delay, anchored at the later of the fallback window opening and the first moment this node saw live paid demand for that attempt: the primary publishes an epoch with a single transaction as soon as it has demand, whatever the load. The follower's `health` output, telemetry and Telegram `/status` say whether it currently counts the primary as alive.

Duplicates resolve cleanly. Both keepers read finalized state first; a fulfillment preflight that fails because another submitter already settled the request, or an epoch preflight that fails because another committer already published, is recorded as nothing to send, not as a rejection. Batch members settled elsewhere are skipped on chain, a duplicate that still reaches the chain reverts and resolves from chain state, and a still-pending transaction for work settled elsewhere is replaced by a 21,000-gas nonce cancellation; those reverts and cancellations are the only wasted gas, and they occur only when the primary was slower than the delay. Whichever wallet publishes first defines the epoch; the two keepers may hold different packets for it, and both are valid. The keeper share of a request is paid to the wallet that submitted its accepted proof when the registry authorizes that wallet, so a follower earns the share of the requests it serves; it still needs its own gas funding, and a fulfillment from any other submitter pays `committer()`. Both keepers read rounds from the drand relays.

Health observations, telemetry reports and Telegram status name the role (`role` in `health` output). With the same `NEON_DB`, both keepers can index the same public chain history: a follower indexes only while the shared cursor is its own or has not moved for 60 seconds, rows are upserted by chain identifiers, and a transaction lock with a cursor check makes a concurrent indexer retry from the newer cursor. The public `keeper_status` row stays single: a primary always writes it, while a follower writes it only when the row is its own or 90 seconds older than its own observation, so while both run the primary's status is shown and during a primary outage the follower's is. The `role` column is an additive schema change. Telegram polling for `/status` and `/keeper` is on by default only for a primary (`TELEGRAM_COMMANDS`); a follower can share the network's bot token and chat in notification-only mode without competing for commands.

## Ticks and chain events

With work open (a live request, an unresolved transaction, an operator sweep) the keeper ticks every POLL_MS; with nothing open it ticks every IDLE_POLL_MS (default the larger of POLL_MS and 1 second, at most 20 seconds). Optional WS_URLS (`wss://`, comma-separated, tried in turn) subscribe to new blocks and to the coordinator's and registry's logs; a pushed log from any other address is ignored, since not every endpoint applies the subscription's address filter. While a subscription is live, open work ticks on each pushed block (keeping POLL_MS between ticks, and at most one second without a push), and an idle keeper ticks at once on a request or any other service event, otherwise every 5 seconds. A pushed request therefore reaches the next tick within one block; without a subscription, within IDLE_POLL_MS. Events only decide when to tick and what to re-check: every decision still comes from HTTP reads at the finalized block, so a missed or repeated event can delay work but not change it. Each (re)subscription forces the pin and authorization checks and backfills the missed blocks' logs over HTTP in 500-block ranges (up to 5,000 blocks). A subscription silent for 20 seconds is replaced; an endpoint on another chain is dropped; while none is live the keeper polls. A round keeper's subscription follows less, and its idle heartbeat is its own: see "Polling and subscriptions" under Round mode.

## Fleet drill

`scripts/fleet-drill.ts` runs the failover and load scenarios against real keeper binaries on a local chain configured like Arc: 500 ms blocks, no automine and no time fast-forwarding, so deadlines, join delays and fallback windows pass in real time. The epochs come from a test drand network that a fake relay serves and the real BLS verifier checks; the blocks mined at the start to reach its first epoch keep their timestamp. Every scenario is expected to pass here before it is repeated on a network.

```sh
npx hardhat run scripts/fleet-drill.ts
DRILL_SCENARIOS=healthy-burst DRILL_REQUESTS=100 DRILL_STEADY_SECONDS=30 npx hardhat run scripts/fleet-drill.ts
```

The drill builds the release keeper of the current revision before it starts, and the integration suite builds the debug one, so neither can pass against a stale binary; `DRILL_BINARY` runs a specific build instead.

Each scenario is a data entry: how the load arrives (burst or steady), how many service lanes run, which fault is injected when (kill a process, block one keeper's RPC endpoint, restart a keeper) and the thresholds the result must satisfy. Every keeper gets its own wallet, journal, lock scope and RPC endpoint, so a single lane can be isolated while the others keep running. The measurement comes from chain data through the same reader as `scripts/failover-report.ts`: requests served and gas used per wallet, refunds, unserved requests, reverted keeper transactions, nonce cancellations, duplicate attempts as a share of the requests, and the seconds from the fault to the first fulfillment a follower lands after it. The scenarios cover both ways a follower can come in: a burst deep enough to bring it in on its own, and demand too light and too young for that, where only a chain-dead primary can. The run fails if any scenario leaves its thresholds. It is a drill rather than part of `npm run check`: a full run takes minutes of wall-clock time by construction.

## Retention, restart and moving hosts

Unused local snapshots retire after 50 epochs when no live demand or unresolved transaction depends on them. Periodic bounded compaction removes eligible terminal proof/calldata/raw transaction bodies but retains identity, status and receipt metadata. It does not delete history rows or pending telemetry reports. Published packets remain in chain logs; unpublished packets have no chain copy. SQLite can reuse freed pages without immediately shrinking the file.

Use a process supervisor or Docker restart policy. Reboot recovery uses the same journal and keys; it is not dependent on receiving every live event. Expired requests remain claimable through refundRequest(id). A callback error after accepted proof is paid service and can retry only the same result.

For a host move, stop the old process and restore consistent state/lock/WAL and key backups at the same container paths. For a transaction-key change, drain/stop the old keeper, have the owner rotate the registry committer, then use the reviewed drained migration to the new wallet and restart. Keep the VRF key unchanged. See MIGRATION.md and ../deploy/docker/README.md.

## Observability

health --db <absolute-path> reads local progress. `sweep --amount|--keep <USDC>` queues a transfer of keeper earnings to the coordinator fee recipient, which the running keeper sends on its own nonce lane (`--status`, `--cancel`; see deploy/docker/README.md). Optional HEALTH_API_URL and HEALTH_API_KEY deliver durable summaries. Optional Telegram notifications and read-only /status and /keeper commands use only the configured chat. Observations carry age; stale health, balance and authorization are unknown. Telegram is best-effort and cannot block settlement. See TELEGRAM.md.

Health faults: `preparation_stalled` (a request this keeper is responsible for has waited PROGRESS_STUCK_SECONDS without a journaled proof: every request for a primary; for a follower, its lane once it has joined the queue and any request at the safety age; a request that expired unprepared after such a wait keeps the fault until a later proof or for 15 minutes; a request another keeper served ends its wait), `settlement_stalled` (allowed work without progress for PROGRESS_STUCK_SECONDS; a follower counts only sends it is responsible for and drops the observation once it has no prepared open request or transaction of its own left), `fee_budget_exceeded` (a required send exceeds a configured cap; see Configuration), `epoch_stalled` (live paid demand whose epoch work is blocked, whose saved packet is older than the attestation freshness bound or whose beacon fetches have kept failing for 10 seconds, for PROGRESS_STUCK_SECONDS), `epoch_recipe_unsupported:<recipe id>` (the catalog in force selected a recipe that is not a drand beacon, so the keeper did not prepare that source; reported at once, with or without demand, until an epoch's selected source is supported again), `nonce_stalled:<nonce>` (unresolved lane older than NONCE_STUCK_SECONDS), `node_rejected:<reason>`, `finality_mismatch`, `finality_unconfirmed` and `finality_audit_stalled` (soft finality; see below), `round_unavailable` (round mode: live requests have waited more than 10 seconds on a due round whose fetches keep failing; see below), `round_rpc_error` (the same wait, when the last failure was the keeper's own read of the chain), `clock_behind` (round mode: this machine's clock is more than 15 seconds behind the decision head's time; see below), `tick_failed`, `rpc_rate_limited` (every RPC endpoint was rate limiting, so the last tick could not run; degraded rather than failed), and the reader-side `observation_stale` and `observation_clock_anomaly`. With `--once`, an unhealthy assessment is a nonzero exit.

The implementation is a supervised service, not a public delivery SLA or external cryptographic audit. Local checks include proof/callback/refund behavior, crash recovery, 30-second outage gaps, delayed RPCs, UUPS changes and storage continuity. Actual network gas and fee economics require measured validation.

## Round mode (`COORDINATOR_KIND=round`)

`COORDINATOR_KIND` names the coordinator the keeper serves: `epoch` (the default, and the only value Arc accepts) or `round`, a round coordinator that binds each request when it is made to a future drand round and has no registry, no epochs and no target block. Robinhood Chain requires `round`; the local test chain and nitro-testnode take either. Every other chain refuses `round`: a round keeper runs only on a chain whose policy names it. The registry kind and the block nudge of the earlier epoch design are gone: `REGISTRY_KIND`, `BLOCK_NUDGE` and `BLOCK_NUDGE_AFTER_MS` are not read.

A round keeper refuses every setting that belongs to an epoch coordinator: `EXPECTED_REGISTRY_IMPLEMENTATION_CODE_HASH`, `APPROVED_NEXT_REGISTRY_IMPLEMENTATION_CODE_HASH`, `REGISTRY_KIND`, `BLOCK_NUDGE`, `BLOCK_NUDGE_AFTER_MS` and `EPOCH_API_ENDPOINTS`. Off the local test chain it requires the round coordinator's proxy, implementation and protocol configuration hashes. It takes no default sized for Arc: `MAX_FEE_PER_GAS_WEI`, `MAX_TX_COST_WEI`, `MIN_PRIORITY_FEE_WEI`, `MAX_PRIORITY_FEE_WEI`, `SWEEP_MIN_RESERVE_WEI`, `NONCE_STUCK_SECONDS` and `MAX_GAS` must be written down on every chain. Robinhood Chain also requires `FEE_COVERAGE_BPS` written down and at least 12500.

At startup a round keeper reads the round coordinator alone: its proxy and implementation pins, its VRF key (`publicKeyX`, `publicKeyY` and `keyHash`, which must be the hash of the operator's key), its configuration pin, `ROUND_LEAD()`, `pricing()`, `beaconSchedule()`, `beaconCount()` and `getBeacon(id)` for every beacon its book has registered, and its keeper roles (`keeper()`, and `isBackupKeeper` for a follower or a wallet that is not the keeper). A registration never changes, so each is kept for the process; a beacon a request names later is read when its round is due. The publishing right is the coordinator's keeper roles: a primary runs as `keeper()`, a follower as an allowed backup keeper. Discovery reads requests with `getRoundRequest` and journals each live one with the beacon and round it is bound to, the fingerprint of its seed inputs and its sealing lag (table `round_demand`): the time this keeper first saw the header of the request's block (a pushed head from `WS_URLS`, or a decision head a tick read) less the block's time. When this process saw no header of that block the lag is measured at discovery, which is later, and the log says so (`lag_from`). A lag over 3 seconds is logged at warn. Round demand is the set of rounds that live requests wait on. Each tick also reads the oldest open requests again to see which the chain has served or refunded.

The round lane keeps one row per round that live requests wait on (table `round_work`). A round is fetched once the keeper's wall clock reaches its scheduled time, `genesis + (round - 1) * period`, and never before: the relays that hold requests answer as soon as the round exists, and the chain's own clock stops on an idle chain. When the decision head's time is more than 15 seconds ahead of the wall clock, the machine's clock is behind: the lane takes rounds due by the head's time instead and keeps serving, the health fault `clock_behind` stands until new blocks have shown the clock right for ten minutes (a head that is only old, on an idle chain, says nothing), and Telegram asks the owner once, in Turkish, to set the clock right; a restart does not ask again. If the round coordinator already has the round at the decision head (`roundRandomness` is set, because another keeper's fulfillment verified it), its signature is taken from the round's `RoundVerified` event instead; when no such event is found from the block of the round's oldest live request on (the round was verified serving an earlier request), the round is fetched from the relays and held to the coordinator's randomness: its signature's sha256 must be it. Otherwise every relay of `DRAND_RELAYS` whose circuit is closed is asked at once, with the same relay client, bounds and circuits as an epoch keeper's (above), in the round keeper's own table `drand_relay_breaker`; the first well-formed signature the coordinator accepts (`checkRoundSignature`, an `eth_call` with a gas limit of 1,000,000 written down; it needs about 460,000) is kept, with the round's randomness, sha256 of the signature, and the row is `verified` for good. A round keeper also excuses a relay's HTTP 5xx while the round is recent, as it does 404, 425 and no answer: relays have answered 500 for a round not produced yet. A fetch that fails is tried again every 2 seconds while live requests wait on the round; after 10 seconds of failures the health fault `round_unavailable` is raised, or `round_rpc_error` when the last failure was the keeper's own read of the chain (the coordinator's verdict on a signature, or its record of the round) and not what the relays did; the fault clears as soon as no live request waits on such a round. At most two fetches run at once. A row whose round no live request waits on any more is deleted. Each verified round is logged with how long after its scheduled time it was verified.

A request is proved once its round is verified. Each tick claims the pending requests whose round the lane has verified (at most eight, four proved at once), reads each again at the decision head with `getRoundRequest`, and computes its seed as the coordinator's `_seed` does: `keccak256(abi.encode(SEED_DOMAIN, chainid, coordinator, keyHash, requestId, consumer, clientSeed, mappingHash, requestBlock, beaconId, round, roundRandomness))`, with `SEED_DOMAIN = keccak256("D20_VRF_ROUND_SEED")` and the round's randomness from `round_work`. Until one seed has matched in a process, the keeper also asks the coordinator for the request's `getProofContext(id, signature)` (an `eth_call` with a gas limit of 1,000,000 written down) and proves nothing while the two differ; after one match it computes the others alone. The proof is made by the same prover as an epoch keeper's, and journaled with the fingerprint of the request it was made for, beside the calldata of the single fulfillment `fulfillRandomness(id, proof, signature)`.

Sends follow an epoch keeper's single and batch paths, with these differences. Every request is read again at the decision head (by its block number, never `latest`) before anything is signed. A revert (`UnknownRequest`) means the coordinator does not have the request only where its `nextRequestId` at the same block has not reached the id; otherwise the endpoint has not got that block's state, and the read fails like any RPC failure. A request the coordinator does not have is left out of the send and read again until its deadline, and its fulfillment in flight is not cancelled for it: one read is not enough to call it gone. The finality recovery, on a replacement the endpoints confirm, makes it `vanished`. A `vanished` job is never final: the chain as it is can hold its request again, or reuse its id for a new one, so discovery keeps its cursor at or below the lowest vanished id, and discovery, the tick's reads of open requests and the recovery make the job `pending` again when the chain has a live request under its id. One whose fingerprint is not the one its proof was made for loses its proof and returns to `pending`, and is proved again for its new fields; a fulfillment in flight that serves such a request is never sent again or replaced: its nonce is cancelled, and the request proved again once the cancellation settles; the observation `request_moved` is recorded in the journal (`observation:request_moved`: how many, the last one and when). A batch is `fulfillRandomnessBatch(rounds, ids, proofs)` with one signature for each distinct round of its members, and every fulfillment carries its round's signature even when the coordinator has verified the round already, so that a block replaced before inclusion cannot make it revert. The escrowed fee is the request's `feePaid`.

The gas limit is never below what the coordinator's guards need behind its proxy, which forwards 63/64 of the gas left: `64/63 × (140,000 + Σ(cb + cb/63 + 400,000) + rounds × 411,349)` and the transaction's own cost around it, plus the payload's L1 component with `L1_GAS_MARGIN_BPS` (the model of the round contracts' gas tests, `keeper/src/round_gas.rs`, held to the TypeScript model's numbers in `keeper/tests/fixtures/round-gas-model.json`), and a margin of 1% of both, at least 5,000: the model's own terms clear the measured least limits by only about 800 gas, and a node's `eth_estimateGas` (geth's estimator, which Nitro runs) returns the top of the last window its search halved, not the least limit that passes. It tries the gas the call used, then twice that, and halves the window until it is narrower than 1.5%; when the doubled guess passes and every halving fails, as for Robinhood testnet's first fulfillments, the estimate is at most 128/127 of the least limit (0.79%). Those two were estimated at 1,145,832 and 2,205,422 against least limits of 1,143,179 and 2,200,842 with the keeper's L1 component, and the model now gives 1,154,611 and 2,222,851. Every round a fulfillment lists counts as one it verifies, the request's round of a single included, even when the coordinator has it at the decision head. `eth_estimateGas`, padded as an epoch keeper pads it, sets the limit when it is higher. An estimate more than 1.6% above the least limit, which the estimator never returns on any path, is logged at warn: the chain then needs more than the model allows.

The fee gate prices a fulfillment on the gas it can use, not on `eth_estimateGas`, whose callback reserves are never spent: `base fee × (bound + L1 component with the margin)`, where the bound is 223,400 for a single, plus 234,300 for its round (217,300 and 17,000 for Robinhood's costlier drand hash-to-curve), or 79,500 for a batch plus 161,400 a member, 222,600 a listed round and 250 a member and round; plus each callback's gas limit in full, 5,500 for each VRF hash-to-curve candidate after a proof's first (the prover counts them) and 17,200 in case the coordinator's earned fees were just withdrawn. Every listed round counts, cached at the decision head or not. The escrowed fees must cover `FEE_COVERAGE_BPS` of that cost (Robinhood requires at least 12500), and the keeper's own share of them, at the coordinator's `keeperFeeBps()` read for each send, must cover the whole cost: the keeper's gas is paid from its share, never from the treasury's or the operator's. At coverage 12500 and share 8000 the two are the same rule; the share binds when the owner lowers it. A fulfillment is signed only when the wallet holds its up-front cost, gas limit × max fee per gas (twice the base fee, no tip on Robinhood), which the node requires in full: a batch shrinks to the members the balance covers, and a request the balance cannot cover alone is not signed, so that it stays prepared for a follower and no nonce waits on bytes the node refuses. The owner is then asked once, in Turkish, to fund the wallet with what about 20 fulfillments cost at that price, and asked again only once the wallet has held the cost it lacked with a quarter to spare; the same notice is sent when the node refuses an already-signed replacement, cancellation or fill for want of funds. A round keeper's English low-balance alert (`TELEGRAM_LOW_BALANCE_WEI`) is likewise once per episode. Nothing fails a tick or stops the process meanwhile. A batch that is not covered drops its lowest-fee member, and a single that is not covered waits as a budget deferral.

Before a batch is estimated it keeps only the members, from the front, whose gas limit with every distinct round of theirs counted fits `MAX_GAS` and `MAX_TX_COST_WEI` at the price it would pay. Robinhood testnet's per-transaction limit is 32,000,000 gas, above the 13,000,000 of its profile's `MAX_GAS`; mainnet's is not verified.

An operator sweep of a round keeper is asked and reported in ETH (`sweep --amount 0.05`, its status and refusals), keeps the `SWEEP_MIN_RESERVE_WEI` the operator wrote down (or `MAX_TX_COST_WEI` when larger) and reads the fee recipient from the round coordinator. The Discord proof feed announces an epoch coordinator's proofs only. The public explorer index has no round mode yet and stays off.

A round keeper's journal has none of the epoch lane's tables (`epoch_work`, `epoch_demand`, `epoch_relay_breaker`): it has `round_demand`, `round_work` and `drand_relay_breaker` instead, and names its kind in its metadata. Each kind refuses a journal of the other. An epoch keeper's journal in finalized mode, as Arc runs it, is exactly the journal of 0.4.1, table for table and index for index; a keeper in soft mode adds the table of its marks (`soft_marks`) beside the others.

### Polling and subscriptions

Robinhood Chain makes about 10 blocks a second on mainnet and 4 on its testnet, and an RPC provider bills every call (each member of a batch) and every message a subscription pushes, so a round keeper asks for less than an epoch keeper does. Its subscription (`WS_URLS`) follows only the coordinator's requests (`RandomnessRequested`), keeper role changes (`KeeperChanged`, `BackupKeeperSet`) and upgrades (`Upgraded`); a pushed log of another event or address is ignored, since not every endpoint applies the filters. It subscribes to new blocks (`newHeads`) only while work is open, a live job, an unresolved nonce, an operator sweep or a finality incident, and unsubscribes when none is left. With work open, ticks follow pushed blocks as an epoch keeper's do. With nothing open and the subscription live, the keeper ticks at once on a pushed request and otherwise every `IDLE_HEARTBEAT_SECONDS` (2 to 30, default 30), which finds a request whose event was missed. While it is idle with a live subscription it re-checks its runtime pins and its publishing right every 120 seconds instead of 15 and 30: an `Upgraded` or role event, a resubscription, open work and every signature check them at once. The heartbeat, `SEND_MARGIN_SECONDS` and a 10-second fulfillment round must fit the request's 60 seconds or the keeper does not start; the request's round, at least `ROUND_LEAD` seconds after it, overlaps the heartbeat. An epoch keeper refuses the setting. Without blocks an endpoint may push nothing for minutes, so the subscription sends it a WebSocket ping (not a JSON-RPC call) after 10 quiet seconds (at most half of `WS_SILENCE_SECONDS`) and is replaced after `WS_SILENCE_SECONDS` (5 to 600, default 20) without any frame. A reconnect backfills the logs it missed over HTTP, `WS_BACKFILL_RANGE` blocks a read (default 500), when the gap is at most `WS_BACKFILL_MAX_BLOCKS` (default 5,000). An epoch keeper keeps those defaults whatever the settings say, and no keeper acts on `INDEX_FINALITY`, `INDEX_MAX_BLOCKS` or `INDEX_LOOKBACK_BLOCKS` yet: the explorer index follows the finalized head. A keeper that is given a setting it does not act on says so once at startup. Without a live subscription `IDLE_POLL_MS` applies as before.

The finality audit (`FINALITY_AUDIT_INTERVAL_SECONDS`) and the Telegram status (every 60 seconds: the pins, the head, the balance and the publishing right, about 6 calls) keep their own intervals and add no call to a tick; the `head` mark is only ever the newest block, so the audit reads no block per tick. While blocks are not followed, the first request of an idle spell has its sealing lag measured at its discovery, which the pushed request starts at once (`lag_from=discovery`). Each tick writes the health observation, so `health --max-age` (30 by default, as the Telegram status allows) must exceed the heartbeat with the tick's own time, or an idle keeper reads as stale between two ticks: with the default heartbeat of 30 seconds, give `--max-age` 45 or more, or keep the heartbeat at 25 seconds or below.

What a round keeper asks in a minute (`keeper/src/round_polling.rs`, its real ticks against the scripted chain, every member of a batch counted, Telegram not included):

| Minute | Before | Now |
| --- | --- | --- |
| Idle, no subscription | 196 calls (128 HTTP requests) | the same |
| Idle, subscription | 52 calls and every block pushed: 292 on testnet, 652 on mainnet (4.9 and 10.9 a second); 31 calls (19 HTTP requests), nothing pushed, with a 10-second heartbeat and 15- and 30-second re-checks | 12 calls a minute over two minutes (10 on Robinhood Chain, see below), nothing pushed: 0.2 a second |
| One request served, subscription | about 105 calls, about 350 with pushes on testnet and 710 on mainnet; about 90 calls with a 10-second heartbeat | about 70 calls, about 89 with pushes on testnet and 113 on mainnet |

Of an idle minute's 31 calls with a 10-second heartbeat the six ticks were 18 (the decision head with the block the last tick decided on, in one batch, and `nextRequestId`), the runtime pins every 15 seconds 9, the publishing right every 30 seconds 2 and the audit's finalized header 2. Now two idle minutes ask 24: four ticks 12, the audit's finalized header 4, the pins 3 and the publishing right 1 once in the 120 seconds, and 4 reads of the head mark, which the scripted chain's finalized head (30 blocks behind) passes before the next tick rewrites it; on Robinhood Chain finality trails by minutes and the audit reads no head mark, so an idle keeper asks 10 calls a minute; `FINALITY_AUDIT_INTERVAL_SECONDS=60` halves the audit's reads, to 9.

## A finality mismatch (`FINALITY_MODE=soft`)

A soft keeper decides on the sequencer's latest block and writes down every block it acts on: the block of each settled receipt, of each signature and of each nonce found consumed, and the decision head of every tick. The audit checks those blocks against L1 finality (`FINALITY_AUDIT_INTERVAL_SECONDS`), and every tick holds the chain to the block the tick before decided on. With more than one endpoint, every endpoint is asked, each within a deadline inside the audit's two seconds, so one that does not answer is passed over. A block is final for the audit only at or below the most advanced `finalized` header that is at least ten minutes old (an endpoint that answers the tag with its latest block, or one stuck on an old block, decides nothing), and only when every endpoint that answered shows the same hash for it; when they differ, nothing is made final and the endpoints are asked about the block. A receipt or checkpoint the audit made final and the chain then moved is a mismatch of the block the record names; the recovery from it drops the record, and the next audit records the receipt where the chain has it. A block that is not the chain's any more is a mismatch. The keeper recovers from it by itself: no acknowledgement or other step by an operator is required.

One endpoint's answer is only a suspicion: the sequencer may have replaced the block, or that endpoint may follow another fork. The keeper holds its sends and asks every endpoint of `RPC_URLS` at once for the block's hash and its `finalized` header:

- At least two endpoints agree on another hash, and more of them than show the journal's: the chain changed. The mismatch is recorded durably (`finality:mismatch`, the first one kept, with what the endpoints said), and the recovery below starts in the same tick.
- More endpoints show the journal's hash than show any other hash: the journal's block stands. The journal's hash was itself read from an endpoint, perhaps the one that shows it now, so it is no witness of its own: one endpoint against one is a tie. Each endpoint that showed another hash is put last in the read order for five minutes, the head is read again from the others, and the tick goes on. Nothing is recorded and nothing halts.
- Neither (one endpoint alone, endpoints that do not answer, endpoints that do not agree, or as many on each side): nobody is put on cooldown, the keeper keeps holding its sends and asks again after 2 seconds, doubling up to 30. `health` reports `finality_unconfirmed`, and `finality --status` shows the suspicion with its id. When it has lasted ten minutes, Telegram asks the owner once, in Turkish, to fix or add an RPC endpoint.

A block the last tick decided on that lies above the head of every endpoint that answers is suspected the same way: the sequencer replaced the tip with a shorter chain and has not made as many blocks again. Endpoints that do not have the block confirm that only when no endpoint shows the block at all, over at least three asks and ten seconds, since they may just be behind the one that gave the block. The tick does not fail on it.

A keeper with a single RPC endpoint warns at startup: no second endpoint can confirm a replaced block, so it holds its sends until its endpoint shows the journal's block again or an operator acknowledges the suspicion (below), and Telegram asks the owner once, in Turkish, to add a provider. Use at least two independent providers, better three. In soft mode an endpoint listed twice in `RPC_URLS` is asked once and counts once. A round keeper does not drop an endpoint that does not answer at startup: it holds it out of its reads and probes it again beside its ticks, never inside one, after 10 seconds, the wait doubling up to 5 minutes, and reads from it again once it answers with the configured chain id, the coordinator's code and the pinned implementations. The owner is asked to add a provider only when fewer than two are configured, or when one has stayed out for ten minutes. An epoch keeper goes on with the endpoints that answered at startup, as before. The owner's ten-minute wait for an unsettled suspicion, and for a recovery that keeps failing, counts from when the block was first suspected or the recovery first failed, over restarts, and the owner is asked once per incident.

While the sends are held:

- No transaction is signed or broadcast: a fulfillment, a batch, an epoch commit, a cancellation, a replacement, a rebroadcast, an operator sweep. This is enforced where the keeper signs and where it broadcasts, not only at the start of a tick. Reading, reconciliation and proving go on.
- The process does not exit. A failed tick during the incident is reported and not counted toward `MAX_TICK_FAILURES`, since a restart would come back to the same journal. After a restart the keeper finds the suspicion again from the journal and the chain, or does not when the endpoints show the journal's block.

The recovery moves one step at each tick and starts no new work meanwhile; `health` reports `finality_mismatch` until it is done. It moves its checkpoint to the chain as it is now. It takes back each nonce that the chain does not have although the journal settled it, and each whose receipt is no longer the chain's, lowest first, and never lowers the nonce floor:

- When the journal kept the signed bytes of the nonce's last transaction and they are still worth sending, the nonce is reopened: the request, batch or epoch it served goes back to `submitted`, the marks that justified the old settlement are deleted, and reconciliation settles it again from the chain, finding the receipt where it lies or broadcasting the bytes the journal kept (and replacing them with a cancellation when the request has expired meanwhile).
- When those bytes carry a proof whose input the chain has changed (the seed of a member differs from the chain's, or its input is gone), they would only revert and burn gas. The nonce is filled with a zero-value transfer to the keeper's own wallet instead, priced and capped as a nonce cancellation (`CANCEL_MAX_FEE_PER_GAS_WEI`, above what the nonce's earlier transaction offered; with `GAS_MODEL=arbitrum` the cancellation gas limit, checked against the node's estimate of the transfer with `L1_GAS_MARGIN_BPS`, 1.25 times by default), and the request is proved again for the chain as it is.
- When the journal has no bytes for a nonce the chain has not used (the transfer of an operator sweep is not kept once it is settled), the nonce is filled the same way. One the chain has used is marked as found consumed. A sweep transfer the chain no longer has is not queued again by the keeper: Telegram asks the owner once, in Turkish, to queue it again with `sweep` if it is still wanted.

A mark above the decision head is taken as stale at once when the endpoints confirmed that the chain is shorter; otherwise the endpoint that gave the head may only be behind, and the recovery waits up to 20 seconds for the head to reach the mark.

It then reads the jobs again from the finalized head's time on: one the chain settled gets that state, one whose proof is for a seed the chain no longer has loses its proof and returns to `pending`, one marked served that the chain shows open returns to `prepared`; epochs the registry no longer has return to `prepared` or `pending`; and discovery goes back to the first request of the chain as it is now. When the lane and every mark agree with the chain, the record is cleared, the audit and sending resume, and Telegram tells the owner once, in Turkish, that nothing is required. A step that fails is tried again at the next tick; when it has failed for ten minutes, Telegram asks the owner once to act, with what to do.

The proof context of a request and the epoch registry exist only on an epoch coordinator. The recovery's steps that read them (the seed check of a job or a transaction, and the epochs) run for that coordinator kind only. A round coordinator's keeper reads its jobs again with `getRoundRequest` and its request count with the round coordinator's `nextRequestId`; a request the round coordinator no longer has (it reverts for an unknown id) is `vanished`, and one whose fingerprint changed loses its proof and is proved again. Bytes of a round fulfillment are stale when a request they serve vanished, or when its seed, computed over the fields the chain has now and the randomness of its round (the coordinator's, or that of the signature the transaction carries), is not the seed of the proof: the nonce is then filled instead of broadcasting them. A record the registry refuses to give leaves that epoch as it is rather than holding the recovery up.

`d20dao-keeper finality --db <path> --status` prints the state (`clear`, `suspected` or `recovering`), the mismatch (kind, block, the hash the journal has and the hash the chain has, its id), the marks the audit has not checked, what the endpoints said and the recovery's progress. `finality --db <path> --acknowledge <id>` is optional. With the id of a suspected mismatch it records it, in place of the second endpoint that could not confirm it, and the keeper recovers from it at its next tick; use it only when you are sure the chain changed. With the id of the mismatch on record it records that someone has looked, and changes nothing else.

Every tick writes a `head` mark for the block it decided on, and the next tick checks that block, whether or not the tick did anything. That is deliberate. Discovery, proving and the job states a tick reads from the chain have no mark of their own; the head mark is their evidence, and an idle tick cannot be told apart from one that discovered or proved without marking those writes too. A replaced head block that the endpoints confirm leads to a recovery of reads only: nothing is sent again, it finishes in a tick or two, and the owner's message says that no transaction had to be sent again.

A transaction that is still in flight (never settled) when a block is replaced is not taken back: reconciliation keeps broadcasting it, and cancels it once its request has expired. When its proof input changed, it reverts if it is included.

## Optional public explorer index

An optional [Discord proof feed](DISCORD.md) publishes only accepted proofs to the configured protocol channel. It is independent of Telegram operator alerts and uses a bounded background queue; it never opens an incoming port or stalls settlement.

Set `NEON_DB` privately to enable the independent chain-log indexer. Its `tokio-postgres` transport requires TLS with trusted certificates and hostname verification, plus SCRAM channel binding. A Neon URL containing `sslmode=require&channel_binding=require` is supported without weakening either requirement. The daemon never loads `.env` files itself or prints the connection string or raw database errors.

The indexer reads only the approved registry/coordinator's public chain state and events. The `d20dao_explorer` schema stores public deployment configuration, one exact epoch packet per published epoch (a drand round, or the signed API record of an epoch published before the drand catalog), one exact proof packet per fulfilled request, receipt/block references and small callback/refund/fee event history. Unpublished local snapshots, transaction signing bytes, keys and SQLite paths never enter this database. Expiry is derived from indexed chain time and the request deadline; it is not fabricated from a browser clock. The schema also holds one live `keeper_status` row per deployment, replaced about once a minute: health, fault codes (without details such as node rejection reasons), send mode, the keeper wallet and its balance, the chain head, open paid demand and the last service time. A website treats a row older than two minutes as a stalled or offline keeper. Only the last 64 scanned block hashes are kept, since the reorg check reads just the last indexed block and its lookback anchor.

Scanning runs in a separate abortable task, in adaptive batches of at most 128 blocks up to the finalized head, with bounded request/log counts. Database outages cannot hold the nonce lane or block settlement. One database session is kept across rounds, with TCP keepalive every 30 seconds and a 30-second deadline for connecting (TLS, SCRAM and a resuming serverless compute); it is replaced between rounds when the server or network closed it, after 15 minutes, or after 4 idle minutes, and after a round that timed out inside it. A failed round keeps the session and the registration and is logged at debug level with its class only (`database_connection`, `database`, `rpc_rate_limited`, `rpc`, `chain_not_ready`, `cursor_contention`, `review_required`, `approved_upgrade`, `timeout`); `Public explorer index is behind` is logged once rounds have failed for three minutes, then hourly, and `Public explorer index caught up` when they succeed again. Another indexer advancing the cursor is progress, not lag. A transaction-scoped lock and cursor check prevent concurrent indexers from overwriting newer progress. The durable cursor advances only with the complete batch transaction. Canonical hashes detect reorgs; a 12-block lookback repairs shallow changes, and deeper changes hide the old index while rebuilding from initialization. Historical proxy code must match an implementation identity previously accepted under reviewed keeper pins. After a move to the approved next implementation (`approved_upgrade`) the keeper restarts, registers the new identity beside the earlier ones and indexes on, so every block keeps the implementation that was active at it. The public verifier must still check independent chain data and its own trusted implementation hashes; a database row is not proof of canonical acceptance.

Schema-only initialization can be invoked with `cargo run --manifest-path keeper/Cargo.toml --example explorer_initialize` after supplying `NEON_DB` in process environment. It creates the idempotent schema and probes the database, without inserting production records. No chain deployment or funding is performed. The SQL is in `explorer-schema.sql`.

Epoch publication can refresh more than 1,024 existing requests. These refreshes use durable 128-row keyset pages at one fixed end block, resume after restart and become public atomically with cursor advancement. Changed block identity discards stale staging. Block-end implementation metadata is an observation, not transaction-level execution attribution.

Local integration uses `explorer_local` with a public 31337 RPC/pin fixture and disposable localhost PostgreSQL on port 55439. It ignores `NEON_DB`. The optional PostgreSQL tests exercise atomic cursor advancement, duplicate replay, stale-writer rejection, reorg invalidation, stalled-database isolation, verified TLS and required channel binding, and a round loop that absorbs a lagging chain endpoint, a server-closed session and a rate-limited RPC without a warning, a second registration or an extra session. They use a generated public test CA and a public local password, never production credentials. Always unset `NEON_DB` in daemon test child environments.
